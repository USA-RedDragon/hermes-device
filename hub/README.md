# talaria-hub

[![Release](https://github.com/USA-RedDragon/talaria-hub/actions/workflows/release.yaml/badge.svg)](https://github.com/USA-RedDragon/talaria-hub/actions/workflows/release.yaml) [![go.mod version](https://img.shields.io/github/go-mod/go-version/USA-RedDragon/talaria-hub.svg)](https://github.com/USA-RedDragon/talaria-hub) [![License](https://badgen.net/github/license/USA-RedDragon/talaria-hub)](https://github.com/USA-RedDragon/talaria-hub/blob/main/LICENSE)

The hub of Talaria: one web front end, behind OpenID Connect login, for many [Hermes Agent](https://github.com/NousResearch/hermes-agent) gateways. It is made for a phone first.

Guides: the [API overview](docs/api.md). To install the hub with Hermes and a sandbox in one step, use [talaria-deploy](https://github.com/USA-RedDragon/talaria-deploy). `docs/site/build.sh` builds the pages in `docs/` into a static site with pandoc.

- One list of the sessions on every Hermes backend that you may use, live and stored.
- Open a session and continue it, also a live session that VS Code or the CLI started. The gateway keeps ownership of the session, so you can go back to VS Code at any time.
- Reasoning, tool calls (arguments, progress, result) and the reply stream live, with no refresh.
- New sessions, interrupt, approval prompts with every choice Hermes offers, and the agent's questions (pick one, pick several, or type an answer).
- Notices on the phone when Talaria needs you or is done, through Telegram and Web Push, also for chats nobody has open and for scheduled jobs (see [Notifications](#notifications)). The hub installs as an app.
- Images and files attached to a message, on the page and in Telegram (see [Attachments](#attachments)).
- Images and files the agent shows the user, such as browser screenshots, on the page and in Telegram (see [Files from the agent](#files-from-the-agent)).
- Pages: interactive HTML that the agent writes, opened full screen in a sandboxed frame, with a way to send an answer back to the chat (see [Pages](#pages)).
- Claude subscription accounts as one pool of models, and each account's Claude API key as models of their own, with each account's usage, an API credit estimate and a sign-in from the hub (see [Claude](#claude)).
- Replies in Markdown, with colored code blocks and a Copy button. Model output never becomes HTML, and links open only `http`, `https` and `mailto` targets.
- Bare addresses are links in your own messages, in the text of notice cards and in tool card output: `http://`, `https://` and `www.` addresses open in a new tab, and nothing else does (never `javascript:`, `data:` or `file:`). A closing `.`, `,`, `;`, `:`, `!`, `?`, quote or an unbalanced `)`, `]` or `}` stays out of the link; balanced parentheses stay in. Your text is not rendered as Markdown. Replies link bare `http` and `https` addresses as well.
- A line under the chat title with the model, how full its context is (such as `41k / 131k context`, with a small meter), the subagents that run now by model (such as `subagents: Haiku ×6`), reply speed and the working folder. It opens to pick the model, the thinking level and the chat's Subagents (see [Subagent routes](#subagent-routes)).
- Rename, archive, delete, pin and export chats, and search their titles. The list marks chats that run, replies you have not seen yet, and chats that wait for your approval or answer (see [The message box and the chat list](#the-message-box-and-the-chat-list)).
- An optional Telegram bot (`telegram.*`) that uses the same backends and permissions.
- Optional [talaria](https://github.com/USA-RedDragon/talaria) computer support (`device.*`): users pair their own computers, start or move chats onto a computer and folder from the web page or Telegram, and Talaria runs commands, edits files and serves VS Code there.

The hub speaks the canonical session protocol of Hermes <!-- docgen:const pkg=internal/gateway name=HermesVersion -->`v0.23.1`<!-- /docgen:const -->: JSON-RPC over the gateway's `/api/ws` WebSocket. A contract test (`internal/gateway/contract_test.go`) checks the protocol lines it depends on against a Hermes checkout (`HERMES_AGENT_SRC`, default `~/.hermes/hermes-agent`). Set `HERMES_AGENT_VERSION` to check a newer release. Before a Hermes upgrade, follow [docs/hermes-upgrade.md](docs/hermes-upgrade.md).

## How it works

Each user logs in through the OIDC provider. The hub identifies the user only by the ID token's `sub` claim, which the user cannot change, and maps it to a hub user name with `users[]`. A login whose `sub` is not in `users[]` is refused and gets no session. The `oidc.display_claim` (default `preferred_username`) is shown on screen and never used for access. A user may use a backend when their hub user name is in `backends[].users`, or a group from `oidc.groups_claim` is in `backends[].groups`. Every API call and every stream checks this. The hub stores each user's groups from the last login, so the Telegram bot can apply the same rules. Telegram links and `ui.default_backends` also use the hub user name.

```yaml
users:
  - sub: "<sub of the first user>"
    name: alice
  - sub: "<sub of the second user>"
    name: bob
```

A refused login logs its `sub` (`login refused: sub is not in users`), so you can copy the value from the hub log after a user's first try.

For each backend the hub keeps one WebSocket to the Hermes Webapp listener. It signs in with a dashboard password provider (`POST /auth/password-login`), gets a single-use ticket (`POST /api/auth/ws-ticket`) and dials `/api/ws` with the subprotocols `hermes-gateway-v1` and `hermes-gateway-ticket.<ticket>`. Viewers of the same session share one gateway subscription.

The browser gets each session as server-sent events. Each event has the hub's sequence as its id. When the browser reconnects, it sends the last id back (`Last-Event-ID`) and gets only the events that it missed. If the hub no longer has them, or the id is from another replica, the browser gets a new snapshot. The page owns the stream itself: it reopens it with `?since=<last id>` after a wait that doubles from 0.5 s to 15 s, with jitter, while streams die within 2 seconds of opening, and starts over after a stream stays open 2 seconds. The banner "Connection lost" shows after 5 seconds without such a stream and goes when one is back; a failing chat list retries on the same waits. A new snapshot replaces what the page shows, so the chat matches a fresh load; it keeps the messages the page is still sending and the place of a reader who is not at the end. When the connection to a gateway drops, the hub dials again, replays the missed frames with `session.events.since` and attaches again with `session.resume`.

When a Hermes backend restarts, the hub holds the messages that users send to it. A message is held when `prompt.submit` cannot reach the backend: the gateway answers HTTP 503 `gateway_not_ready`, closes the socket with 1013, refuses with `runtime_draining`, or cannot be dialed. The hub answers `202` with `{"status":"held"}`, tells the chat "Hermes is restarting. Your message will send when it is back.", and sends the held messages of each chat in order when the backend is back. The page gives each message an id (`id` in the `POST .../prompt` body, `hub:` and a UUID) that becomes its `submission_id`, and sends it again under the same id when no answer came, so a lost answer never runs a message twice; the hub holds a message with an id it already holds once, and a snapshot names each pending input by it (`submission_id`). A steer is handed to the running turn even when the request that sent it ended early. It sends each one under the `submission_id` of the first try. Hermes keys an admission by principal, session and `submission_id`, so a retry after a lost answer never runs a message twice. A message that waits longer than `hold.timeout` (default 10 minutes) is dropped, and the chat says that it was not sent. Held messages are kept in the memory of the replica that took them; the hub sends their events to the other replicas through PostgreSQL `NOTIFY`, so a page whose stream runs on another replica also sees them. Events sent while a replica's listener reconnects are lost to that replica. If the connection drops after a message went out, Hermes may have it although the hub got no answer; when the hub then gives up on it, the chat says so.

When the hub attaches to a session, it sets the session's `show_reasoning` control on (`config.set`), so that sessions that VS Code started through ACP also stream reasoning. The gateway reads this flag when a turn starts, so the change shows from the next turn. Set `backends[].show_reasoning: false` to turn this off.

## The page

Every user gets the same page. It opens one chat with the user's default backend (`ui.default_backends`, as `user=backend`, else their first backend), with live activity in plain words. "+" starts a fresh session there (in the sandbox, when the backend has one); the arrow next to it picks the sandbox or one of the user's computers. "More" opens all backends and sessions, and each tool step keeps its details behind "details". Users differ only in which backends they may use.

When a reply is done, its tool steps fold into one line ("Read a file, ran a command (3.4 s) · 2:14 to 2:15 PM") that opens to show them. File edits show their diff and commands show their output.

Every message, tool card and notice card shows when it happened, in the browser's time zone and in 12-hour form (`internal/web/static/times.js`). A time today reads `2:14 PM`; an earlier day reads `Wed Nov 11, 11:52 PM`, with the year when it is not this one. A user message and a reply have a small time line under them. A finished tool card shows `2:14 PM · 329 ms` (when it finished, how long it ran), a running one `Running · started 2:20 PM · 3:12` with a live counter, and a notice card puts the time after its status (`Completed · 2:41 PM · ran 38 min · Sonnet · 64 calls`; "ran" is the run length the notice itself reports). Hover a time, or hold a finger on it, for the full `Thu Nov 12 2026, 2:14:07 PM CST`. Only measured times show. The hub stamps each event with the time it arrived (`at` in the event stream, from the hub's clock), and rows of a loaded chat carry the `timestamp` Hermes stored. So a tool card from the loaded history has a finish time but no run length, since Hermes stores no start or duration for it, and an event of a turn that was already running when the hub subscribed has no time. Where a time is not known the page shows none.

Each tool call is a card with the look of a notice card: a line icon, a one-line title in plain words, a status line that leads with the result, then the time and how long it ran, and a chevron that opens the details. The card takes everything from the call and its result as Hermes sent them, so nothing needs the backend to change (`internal/web/static/toolcard.js`, run against `internal/web/testdata/toolcard/cases.json`). A failed call has a red icon and a red status. The title and status by tool:

| Tool | Title | Status |
| --- | --- | --- |
| `terminal` | `Ran <command>`, or `Started in the background: <command>` | `Exit N`, with ` on <computer>` when the chat runs on one of the user's computers; `Running in the background` |
| `process_manage` | `Stopped background command <command>`, `Waited for background command <command>`, `Checked`, `Read the output of`, `Sent input to`, `Listed background commands` | `Stopped`, `Exited N`, `Still running after waiting 38 s`, `120 lines`, `2 commands` |
| `delegate_task` | `Started subagent: <goal>` (`Started 3 subagents`), `Message to subagent: <goal>`, `Stopped subagent: <goal>`, `Listed subagents` | `Running in the background`, `Delivered at its next step`, `Stopped` |
| `agent_send` | `Message to chat <name>`, `Message to parent` | how it was delivered |
| `search_files` | `Searched files for <pattern> in <path>` | `3 matches in 2 files` |
| `read_file` | `Read <file name>` | `120 lines` |
| `write_file`, `patch` | `Wrote <path>`, `Edited <path>` | `+3 -1` |
| `web_search`, `web_extract` | `Searched the web for <query>`, `Read <host>` | `5 results`, `2 pages` |
| browser, memory and skill tools | `Opened <host>`, `Clicked <ref>`, `Saved to memory`, `Read skill <name>` | `Done` |
| any other tool | the tool name and a short summary of its arguments | `Done` |

A background command or a subagent that a later call names (a `process_manage` kill or wait, a `delegate_task` steer or stop) shows its command or goal, taken from the call's own result or from an earlier call of the chat; when neither is known, the card shows the id. Hermes may call a tool through its `tool_call` wrapper; the page reads the wrapped call, so a loaded chat shows the same cards as a live one. The raw call and the output sit behind the chevron, in labeled blocks (Command, Call, Output, Diff, Matches, Goal, Message) in a scrollable monospace box with a Copy button each; a command keeps its syntax highlighting. The card has the width of the chat and its title is cut with an ellipsis, so it fits a phone and the extension's chat.

The context readout comes from the `usage` object that Hermes sends in `session.usage` during a turn, in `message.complete` and in the session's snapshot: `context_used` (the tokens of the last request) of `context_max` (the model's window). Before the first reply after a restart, only the window (`context_length` in the snapshot info) is known, so the line shows only that. The meter turns the warning color at 80 percent. When Hermes summarizes older messages to make room (a `status.update` of kind `compacted`, or a higher `compressions` count in the usage), the chat gets the note "Older messages were summarized to make room." After a model switch the line drops the old window, and shows the new one after the next reply, since Hermes builds the new model's agent only then. A leading `~` means Hermes estimated the count.

Chat changes use the gateway's `session.mutate` (rename, archive, delete, model), fenced on the session's revision. The model list comes from `model.options` and shows only models of providers that Hermes is signed in to. The thinking level is `config.set` with the key `reasoning`; Hermes applies it from the next turn. A chat that is working or has messages waiting cannot be deleted.

Syntax colors come from [highlight.js](https://highlightjs.org/) 11.11.1 (BSD-3-Clause), in `internal/web/static/vendor`.

## The message box and the chat list

- **One send button.** With no turn running, it sends and is off while the box is empty. While a turn runs and the box is empty, it is a red stop square (Esc does the same). While a turn runs and the box has text, it sends the text to the running turn as a steer (see the hub's `steer` flag on the prompt route). The box grows with its text up to a limit. The paperclip on the left attaches files.
- **Commands and files.** A `/` at the start of the box lists the commands from Hermes (`GET /api/sessions/<backend>/<session>/commands`). An `@` lists the files and folders of the chat's folder on its computer or in the sandbox, through the same folder route as the file viewer, so the computer's roots and refusals apply. A pick inserts the path relative to the chat's folder as `@path`, which the agent reads with its own tools; Hermes does not expand it. The arrow keys move, Tab or Enter picks, and typing filters. The list matches names, aliases and descriptions: a command or alias that equals or starts with what you typed comes first, then skills that start with it, then names and descriptions that contain it. A command that matched through an alias shows it, such as `/compress (alias /compact)`.
- **Saved prompts.** Each user keeps a library of prompts on the hub, so every browser, the page chat and Telegram see the same list. In the box, `/prompt:` lists only the saved prompts whose names start with what follows the colon, and a `/` alone lists the commands first and then the prompts. Up and Down choose, Enter or Tab inserts and Esc closes. A pick puts the prompt's text in place of `/prompt:<name>`, to edit before sending; it never sends by itself. Settings > Prompts adds, edits, renames and deletes them. A name has at most <!-- docgen:const pkg=internal/hub name=MaxPromptName -->`64`<!-- /docgen:const --> letters A to Z, digits and dashes, unique for the user in any case, and a text at most 64 KB. A user keeps at most <!-- docgen:const pkg=internal/hub name=MaxUserPrompts -->`200`<!-- /docgen:const --> prompts.
- **Drafts.** The hub keeps an unsent message per user and chat (`GET` and `PUT /api/sessions/<backend>/<session>/draft`), saved a moment after the last key, so it follows the user to other devices. The line under the box says "Draft synced". Sending clears it.
- **Message actions.** On hover (on a touch screen, a tap on the message) a message shows Copy and Branch. The user's last message also shows Edit (or press the up arrow in an empty box), and the last reply Retry, with a choice of model. Edit and Retry stop a running turn first. Branch starts a new chat from that message; from a user message, the new chat ends before it and its draft holds that message.
- **Chat list.** A green dot marks a chat that runs, a blue dot a reply the user has not seen, and an amber "Approval" or "Question" badge a chat that waits for the user. Pinned chats come first, in the order the user set: drag a pinned row (on a touch screen, press and hold it for about half a second, then drag), or use Move up and Move down in its menu. A new pin goes to the top. The "⋯" menu pins, marks as read or unread, renames, exports as Markdown (tool steps folded under `<details>`), archives, moves and deletes. Each chat shows how long ago it changed.
- **The line under the title** shows the model or Claude account, how full the context is and the Claude account's plan limits (only the windows the account reports). Meters turn amber at 80%. On a phone it also shows this turn's tokens, and the meters are small rings.
- **Scrolling.** A chat scrolled to its end stays at its end while replies stream in and while anything changes the chat's height: a box that grows to several lines, an attachment, the model panel, a banner, the Activity sidebar, the window's size or a phone's keyboard. A chat scrolled up stays on the same message through all of that, through snapshots and reconnects and while older messages load above it; only scrolling (wheel, touch, keys or the scrollbar) moves between the two, and a scroll that the page's own layout caused does not. New messages that arrive above the end show a button with their count that jumps to the end; so does sending a message. What the reader opened or closed (tool groups, tool cards, notices, "Show full result", thinking) stays so across new text, regrouping, snapshots and reconnects. A search result still opens the chat at its message.
- **New releases.** The page checks the hub's version when its event stream is healthy again after a failure, when the tab comes back and every 5 minutes. It loads a new release only while the tab is hidden, or after a minute with no input, scrolling or pointer movement, nothing typed, no menu, dialog or popover open, no text selected and no upload. The service worker fetches the new files first, and the page keeps the chat, scroll positions, open tool steps, the Activity sidebar, the file viewer, Settings and the cursor.

## The hub API for writing and the chat list

- **Drafts.** The page keeps the text in a chat's message box on the hub, for each user and chat (`GET` and `PUT /api/sessions/<backend>/<session>/draft`), so a draft follows you to another device. An empty draft deletes it. A draft takes at most 64 KB.
- **Saved prompts.** `GET /api/prompts` lists the user's prompts by name, each with `name`, `text` and `updated_at`. `POST /api/prompts` with `{"name", "text"}` adds one (201, or 409 when the name is taken), `PUT /api/prompts/<name>` replaces one and can rename it, and `DELETE /api/prompts/<name>` deletes one (404 when there is none). A name or text that is not valid gets 400 with the reason in words.
- **Steer.** While a turn runs, a message sent with `"steer": true` goes to the turn that runs. The hub sends it as a normal message (`prompt.submit`), so Hermes queues it behind the turn. Then the hub asks Hermes to give its text to the running turn (`prompt.steer_queued`), and the answer has `"steered": true` when the turn took it. The agent reads the text at its next step. Hermes lets a client steer only a message with text and no files, in a chat that the web page, the CLI, the TUI, the desktop app or an editor started. When the turn has no agent yet, Hermes refuses (`steer_unavailable`) and the hub tries again for 3 seconds. Any other refusal gives `"steered": false`, and the message stays in the queue as a normal message. A message with files, and a message that the hub holds while Hermes restarts, never steer.
- **A steer when a turn ends.** Hermes moves a steered message out of the queue and hands it to the turn. If the turn ends before the agent reads the text, Hermes puts the message back in the queue at its old place, and it runs as its own turn when the queue gets to it. If the turn ends before Hermes can hand over the text, the hub gets a refusal, answers `"steered": false`, and the message runs as its own turn. In all cases the message is not lost.
- **A steer and Stop.** When you stop a turn, Hermes drops a steer the turn holds, read or not: its `message.complete` has the outcome `cancelled`, and the hub adds the message's `submission_id` to it. The page then marks the message "The turn stopped before Talaria read this message." with Send again.
- **Stop and send now.** A message that waits for the running turn (queued, or sent to the running turn) has a "Stop and send now" link under it. It stops the turn and runs the message as the next turn (`POST /api/sessions/<backend>/<session>/inputs/<input>/now`, where `<input>` is the admission ID or the submission ID the message was sent under). The hub stops the turn with `session.interrupt`. A queued message then runs when the queue gets to it, after any message queued before it. For a steer, the hub waits up to 15 seconds for Hermes to end the steer with the turn, then sends its text again as a new message at the end of the queue (`prompt.submit`, under a submission ID made from the admission ID, so a retry never sends it twice). The wait and the new message go on when the page closes. When the turn already read the steer, the agent sees the text twice: once in the stopped turn, and once as the new message. A steer that went back to the queue, or that the turn read and finished with, needs nothing more. The answer has the shape of a prompt's answer, with the `id` the message now runs under. A message that no longer waits gets 404, and the message of the turn that runs gets 409.
- **Snapshot of a steer.** A snapshot lists a message that Hermes hands to the running turn with the status `steering`; the page shows it as sent to the running turn.
- **Edit and retry.** `POST /api/sessions/<backend>/<session>/rewind` with `{"text", "retry", "provider", "model", "confirm"}` takes back your last message and all that came after it (`session.mutate` `rewind`, as Hermes' `/undo` and `/retry`). Then it sends `text`, or with `retry` and no text, the old text again. The images of the old message are not sent again; a retry of a message with images says so in `notice`. With `model`, the hub first changes the chat's model; a model that needs a confirmation returns `{"status": "confirm", "confirm", "message"}` and changes nothing, so send the request again with that `confirm`. The answer is the answer of a message, with `removed`, the number of rows that Hermes took back. The hub refuses with 409 while the chat works or has messages waiting, and when the chat has no message of yours.
- **Branch.** `POST /api/sessions/<backend>/<session>/branch` with `{"row_id", "title"}` copies the chat into a new chat (`session.mutate` `branch`), up to and including the row `row_id`, or the whole chat without it. The answer is `{"backend_id", "session_id"}` of the new chat. Hermes records the old chat as the parent of the new chat and copies its settings and folder. The device plugin finds where a chat runs through its parents, so the new chat runs on the same computer and folder, or the same sandbox, as the old chat; a copy of a chat that was taken off its computer runs no commands until you move it. After the copy the hub asks the plugin where the new chat runs. If it would run somewhere else, for example on the Hermes server for a chat on a computer, the hub deletes the copy and answers 409.
- **Transcript.** `GET /api/sessions/<backend>/<session>/transcript` returns `{"title", "messages"}`: the chat's stored rows, each with its `row_id`, oldest first (`session.transcript`, read page by page with no subscription). The rows are Hermes' display rows, as a snapshot has them, with `row_kind` added; a summary of older messages is a `system` row with `row_kind` `compaction`. The page uses it to export a chat as Markdown and to find the row of a message that it showed live.
- **Slash commands.** A message that starts with `/` and a command name goes to Hermes' `slash.exec`, as in Hermes' own desktop app, and not to `prompt.submit`. Through `prompt.submit`, Hermes runs a slash command with the handlers of its messaging platforms, which it does not check for a chat of a local client; `/model` there can write the profile's config. `slash.exec` runs only the commands that Hermes checked for such a chat and refuses the others: the hub answers 400 with Hermes' hint. A command that answers at once returns `{"status": "command", "output"}`. A command that becomes a prompt, such as `/plan` or a skill, is sent as your message. `GET /api/sessions/<backend>/<session>/commands` lists `[{"name", "description", "args", "aliases", "skill"}]`: the commands of `commands.catalog` that `slash.exec` runs, with the aliases that `commands.catalog` gives them, without `/diff` (it reads the Hermes server's folder, not a computer's), the quick commands, the plugin commands and the skills, and `/compress` (alias `/compact`) and `/background` (alias `/bg`), which the hub runs itself (see [Activity](#activity)). `slash.exec` refuses `/compress`, so the hub sends `session.mutate` with the operation `compress` and the argument as `focus`, as Hermes' desktop app does, waits up to 10 minutes for the summary and answers with Hermes' report (`{"status": "command", "output"}`); the page shows the summary as the "Earlier messages were summarized" card. It refuses `/compress` while the chat runs. Commands that only the classic CLI runs stay out of the list. The hub keeps each backend's list for 5 minutes. While Hermes restarts the hub cannot hold a command, so it refuses it with 503. The hub refuses `/diff` itself, since it would read the Hermes server's folder and not the chat's folder.
- **The chat list.** Each row of `GET /api/sessions` has `pinned`, `unread` and `needs`. Pins and read state are for each user: `POST .../pin` with `{"pinned"}` (a new pin goes before the others; each row has `pin_pos`, lowest first, and chats pinned before pins had an order all hold 0), `PUT /api/pins/order` with `{"order": [{"backend_id", "session_id"}]}` to put those pinned chats first in that order (it never changes a chat's `updated_at`), and `POST .../read` with `{"unread": true}` to mark a chat unread or `{"unread": false, "at"}` with the `updated_at` that the page showed. `updated_at` is the chat's last activity (`last_active_at` of `session.list` with `picker`), or its start when Hermes does not say. A chat is unread when you marked it unread, or when it does not work and changed after the time you last read it. The hub keeps the latest read time, and never a time more than a minute after its own clock (the time comes from Hermes' clock). The first time the hub needs your read state, it records that time; a chat that you never read counts as read when it last changed before that time, so that old chats do not all show as unread. `needs` is `approval` or `question` while the chat waits for you, from the approvals and questions that the hub sees. A hub replica sees them for the chats that it follows: the chats that someone has open there, and, on the replica that runs the watch of running chats (only when Telegram or Web Push notices are on, see [Notifications](#notifications)), every chat that runs. Another replica shows `needs` only for the chats that it follows.

## Activity

"Activity" in a chat's top bar opens a sidebar with the work the chat runs beside its turns, with the number that runs now. It has two tabs, each with a Now and a Finished part. A row opens to show a live tail. On a phone the sidebar slides over the chat, and the button shows only an icon and the count. A `delegate_task` step or a background `terminal` step in the chat opens the sidebar on its rows. The chat list shows the same count next to each chat (`subagent.roster`).

- **Subagents** are the children that `delegate_task` starts. The page builds each row from the session's `subagent.spawn_requested`, `subagent.start`, `subagent.thinking`, `subagent.tool`, `subagent.progress` and `subagent.complete` events, and from `GET /api/sessions/<backend>/<session>/activity`, which reads `subagent.list`, `process.list` and `delegation.status`, every 3 seconds while the sidebar is open or anything runs and every 20 seconds otherwise. A child shows under the subagent that started it. An open row of a running subagent shows the end of its live transcript (`subagent.tail`). "Message this subagent" queues text that the subagent reads at its next step (`subagent.steer`), and Stop interrupts it (`subagent.interrupt`). Pause and Resume set Hermes's switch for new subagents (`delegation.pause`): it covers every chat of the backend, and subagents that run go on. Hermes does not say which subagent asks for an approval, so the hub shows an approval in a subagent's row only when the command matches that subagent's last tool call or only one subagent runs; the chat shows it in every case.
- **Background** has the chat's background commands (`terminal` with `background`) and its `/bg` prompts. Stop kills one command (`process.kill`). "Full output" shows what Hermes keeps of a command's output, the last 32,768 characters: Hermes v0.23.1 names no output file for a background command, so there is no file to open. There is no "Run again": Hermes has no method that starts a command again. `/bg <prompt>` (or `/background`) in the message box starts a background prompt (`prompt.background`): a separate agent runs it with the chat's settings, and its answer shows in the row when it is done (`background.complete`). Its tokens come from Hermes's records through the device plugin's usage route. The hub refuses `/bg` in a chat on a computer, and in one taken off its computer: Hermes runs the prompt as a session of its own, so its commands would run where new chats run (the sandbox or the Hermes server) and not on the computer. Hermes stores a background prompt as a chat of its own (`bg_...`). Its row has no link to the chat that started it, so the hub knows it by the `bg_` ID prefix. The hub keeps such chats out of the chat list, the search and Telegram topics, since they belong to the chat that started them. "Open chat" on a finished prompt's row opens its full transcript.

**Run in background.** A running `terminal` card in the chat has a "Run in background" button when the backend's `runtime.describe` lists `tool-background-v1` (from hermes-patches; Hermes v0.23.1 does not). It sends `POST /api/sessions/<backend>/<session>/tools/<tool call id>/background`, which calls `session.background_tool` with the turn's execution generation. Hermes asks the command to yield: it hands its live process to the background process registry, the tool returns to the model, and the turn goes on. The command then shows in the Background tab, where Stop kills it. The hub answers 501 when the backend lacks the capability and 409 when no command of the turn runs. The hub reads the capabilities once per connection, and the snapshot's `tool_background` tells the page whether to show the button.

Every call names the chat, and the hub checks that the user may use its backend. The gateway's own handlers (`gateway/session_ancillary.py`) act only on the children and processes of the named chat, and the hub also checks that the subagent or process is in that chat's own list before it sends `subagent.steer`, `subagent.interrupt`, `subagent.tail` or `process.kill`. `delegation.status` also lists the subagents of every chat of the gateway; the hub passes on only whether new subagents are paused.

**Tokens.** The top bar shows the tokens of the turn that runs (or the last one), in and out, and under that the chat's totals in and out, the share of input that came from the cache and the reply speed, from the session's `session.usage` and `message.complete` usage. In counts every token sent to the model, cached or not (`prompt_tokens`). Hermes counts a turn's output itself (`last_turn_tokens`); the hub works out its input from the counters at the turn's start and adds both to the events as `hub_turn`. When the hub cannot tell where the turn started, for example when Hermes rebuilt its agent and the counters do not match, it shows only the output. On a phone the line shows the in and out counts, the chat's totals and the speed. The sidebar shows the tokens of each subagent (from `subagent.complete`) and background prompt, and the totals of the tab; background commands use no tokens. Subagents and background prompts are not part of the chat's own counts.

## Attachments

The paperclip by the message box attaches files; pasting or dropping files onto the chat does too. Each file shows as a chip, with a thumbnail for an image, until it is sent or removed. The sent message shows them. A chat opened again later shows the images again through the hub's file route (see [Files from the agent](#files-from-the-agent)), and other files by name.

- **Images** (PNG, JPEG, GIF and WebP, found by their first bytes) go to the model. The hub stages each one with `image.attach_bytes`, which the gateway saves in the profile's `cache/images`, and names them in the `attachments` of the `prompt.submit`. Hermes takes up to 10 images of up to 25 MB each. Hermes decides whether the model reads them itself or an image model describes them. When the session's tools have no `vision_analyze`, Hermes most likely has neither, and the hub tells the user that the model may not be able to see the images. For a chat on a computer or the sandbox, the hub also writes each image to the chat's folder there, as it does other files, so the agent's tools can open it, and the message names that copy with a line like the one for other files. The page shows that line as the image's thumbnail, served from the computer, or, once Hermes has stored the message, from Hermes's copy, so one image is one thumbnail.
- **Other files** go where the session's tools can read them. For a chat that runs on a computer or the sandbox, the hub sends the file to the device plugin, which writes it into `.hermes/attachments` of the chat's folder on that device (talaria docs/protocol.md section 9). For a chat that runs on the Hermes server, the hub hands it to Hermes with `file.attach`. The message then gets a line that names the file and its path. A file is at most 32 MB. The plugin takes 2 uploads at a time and the hub stages 4 messages with attachments at a time; more get a note to try again.
- One message takes at most 10 files, 64 MB in all. A message with files cannot be a slash command. Hermes must be up to take the files, so while it restarts the hub refuses such a message with a note instead of holding it; it holds one only when Hermes took the files and then went away before the message itself.
- **PDFs** (files that start with `%PDF-`, or named `.pdf` with `%PDF-` in their first 1024 bytes) go where the session's tools can read them, as other files do, and the hub also reads them itself, since Hermes' `pdf.attach` is not served on the gateway's socket. The hub runs `pdftotext -layout` for the text and `pdftoppm` for page images, <!-- docgen:const pkg=internal/pdf name=ImageSide -->`1280`<!-- /docgen:const --> pixels on the long side (about 120 dpi for a Letter or A4 page). The message gets a line that says how many pages the PDF has and which ones are shown, then the text between `<untrusted-pdf-text>` markers with a random id, marked as data from the file and not from the user. One message carries at most <!-- docgen:const pkg=internal/service name=maxPDFText -->`60000`<!-- /docgen:const --> characters of PDF text, shared by its PDFs, and the hub reads text from at most <!-- docgen:const pkg=internal/pdf name=MaxPages -->`2000`<!-- /docgen:const --> pages of each; the agent reads the saved file for the rest. The first pages go to the model as PNG images in the slots of the 10 images that the user's own images leave free. The page shows a PDF with its page count; under "pages" on its chip the user can pick the pages to show, such as `3-10`, and the hub then reads the text of those pages only. Text in the PDF that looks like these markers or like the hub's notes is changed so it cannot pass for them. An encrypted or damaged PDF, or one whose text takes too long or too much memory to read, goes as a plain file, and the user gets a note that says why. When rendering a page takes too long, the agent gets the text and the pages rendered before it.
- The hub runs the PDF programs (poppler-utils, in the container image) with a clean environment, in a new directory under `TMPDIR` that it deletes afterwards, with a 60 second timeout for each PDF and limits of 192 MB of address space and 60 CPU seconds for each program. It reads one PDF at a time, so the programs fit in a 512 MiB pod next to the hub. The PDFs of one message get at most 2 minutes, and at most half of the time the caller has left (a Telegram message has 30 seconds). At startup the hub removes work directories older than 10 minutes that a stopped hub left behind. Without poppler-utils on `PATH` the hub logs a warning at startup and PDFs are plain files.
- **Notes Hermes adds.** Hermes and its plugins append notes to a user message for the model: recalled memory (`<memory-context>`), the Subagents rule and the waiting guidance of the subagent-routes plugin, and the notes about skills that changed or an interface that switched. They are not what the user typed, so the page, the page chat, the exports and Telegram's "sent elsewhere" echo leave them out, with the blank lines before them. A note is left out only when the message ends with it and it has Hermes's exact opening and its closing bracket or tag; the model still gets the whole text.

## Files from the agent

The agent shows a file to the user with standard Markdown in its reply: `![description](/absolute/path.png)` for an image and `[name](/absolute/path/file.pdf)` for any other file, with the path in angle brackets (`![description](</absolute/my file.png>)`) when it has spaces. The path must be absolute. A `MEDIA:<path>` line still works, as for Hermes' own messaging platforms (`gateway/platforms/base.py` `extract_media`). The file can be on the Hermes server or on the computer or sandbox that runs the chat. The talaria device plugin's `browser_screenshot` tool saves a screenshot of a browser tab and tells the model to put such a line in its reply. The page shows the file in place of a Markdown image or link, and hides a `MEDIA:` line and shows the file after the text: an image inline, which opens full size, a card that opens an HTML file as a [page](#pages), or a chip that downloads any other file. A `browser_screenshot` tool card shows the screenshot too. Telegram gets the reply text without the `MEDIA:` line and with each Markdown image or link of a file as its description or label, then each image as a photo (a file when Telegram refuses the photo, or when it is over 10 MB) and each other file as a document, up to 50 MB, except an HTML file, which gets a link to its page. The bot sends at most 10 files of one reply. `MEDIA:` lines in code blocks, inline code examples and quotes stay as text, and so do Markdown images and links in code. Remote image URLs and relative paths are ordinary Markdown.

The page asks `GET /api/sessions/<backend>/<session>/media?path=<path>`, and the hub serves the file only when all of these hold:

- the user may use the backend;
- a reply of that chat names the path with a Markdown image or link, or a `MEDIA:` line, a `browser_screenshot` result of that chat names it, or a message of that chat names it as an attached image (`[Image attached at: <path>]` or `@image:<path>`);
- the path is absolute and clean, with an extension Hermes delivers.

The hub then reads the file from one of two places:

- **The Hermes server**, when the path is under one of the backend's `media_roots`, or, when it has none, is an image in a `browser_screenshot` folder (`<dir>/cache/screenshots/hermes-device/<session>/<file>`) or among attached images (`<dir>/cache/images/<file>`). `<dir>` can be any folder, so on a host with more than one Hermes home, set `media_roots` to this backend's folders, such as `<HERMES_HOME>/cache`. The hub reads it through the Hermes web server, the way the Hermes Webapp page downloads a file: `POST /api/files/ticket` mints a ticket bound to the path, and `GET /api/fs/download` with that ticket streams the file.
- **The computer or sandbox that runs the chat**, for any other path, and for a path under the media roots that the server does not have. The hub asks the talaria device plugin (`GET /api/plugins/device/sessions/<session>/files?path=<path>`, talaria docs/protocol.md section 9), which reads the file over the device's exec leg from the device that serves that chat only. The plugin applies the read rules of file tools there: the path and its real path must be inside the device's roots and not a credential path, the last part must not be a symbolic link, and the file must be a regular file with one hard link, at most 32 MiB. A chat that runs on the Hermes server gets no device files. At most 2 such reads of one backend run at once; the others wait. Browsers may not cache device files (`Cache-Control: no-store`); server files keep `private, max-age=300`. A Telegram chat gets each file the reply names, so in a group every member gets the device file too.

An image (PNG, JPEG, GIF or WebP by both its extension and its first bytes) comes back inline as that type; anything else comes back as `application/octet-stream` with `Content-Disposition: attachment`. Every answer has `Content-Security-Policy: default-src 'none'; sandbox`. A file is at most 64 MB from the server. When the computer is offline, the page gets `503` and Telegram a note that says so. Device files need a talaria device plugin with the read route; with an older plugin they are not shown.

## Pages

A page is an interactive HTML document that the agent makes for the user, for any purpose: a report, a dashboard, a list of entries with checkboxes, a form or a design sketch. A page needs buttons that answer only when its purpose needs them. The agent writes the page in its reply as a fenced block whose info string is `page`:

````
Here are the candidates.

```page
<!doctype html>
<title>Pick entries</title>
...
```
````

The block also opens with `html page` or `hermes-page`, and closes with a fence of the same character that is at least as long. A block inside another fenced block, in a quote, or not closed stays as text. A reply can have more than one page. The page block works wherever the chat runs (the Hermes server, a sandbox or a computer), because the page travels in the reply. An HTML file (`.html` or `.htm`) that a reply names with `MEDIA:<path>` is also a page, under the rules of [Files from the agent](#files-from-the-agent), on the Hermes server or on the chat's computer or sandbox.

The chat shows a card with the page's `<title>`, the label Page and an Open button in place of the block. Open shows the page over the chat with Back, Reload and Download. Its address is `#/page/<backend>/<session>/<ref>`, where `<ref>` is the page's id (the first 32 hex digits of the SHA-256 of the block's text) or the file's path. The browser computes the id with Web Crypto, so the hub must be served over HTTPS or from localhost. Back returns to the chat and keeps the page's state until another page or chat opens. Telegram gets a link to that address for each page, since Telegram cannot run one.

The frame loads `GET /api/sessions/<backend>/<session>/page?id=<id>` (or `?path=<path>`). The hub serves the page only to a user who may use the backend, only when a reply of that chat has the block (or names the file), and only to a frame: a request whose `Sec-Fetch-Dest` is not `iframe` is redirected to the page's address. `GET .../page-info?path=<path>` answers the title of a file page.

Pages are isolated from the hub and from each other:

- The frame has `sandbox="allow-scripts allow-forms allow-modals allow-popups"` without `allow-same-origin`, and the answer has the same flags in a `sandbox` CSP directive, so the page runs in a new opaque origin even if it is loaded some other way. An opaque origin has no storage: `localStorage`, `sessionStorage`, IndexedDB and `document.cookie` throw, so nothing is kept between loads, nothing is shared between pages, and the page cannot reach the hub's storage or cookies. It cannot read the hub's document (`parent.document` throws) or navigate the hub's window.
- The CSP allows inline script and style, scripts from `https://cdnjs.cloudflare.com/ajax/libs/`, `https://cdn.jsdelivr.net/npm/` and `https://unpkg.com/`, styles from `https://fonts.googleapis.com` and fonts from `https://fonts.gstatic.com`, and images and media from `data:` and `blob:` URLs. It blocks everything else: `fetch`, XHR, WebSocket and EventSource (`connect-src 'none'`), images and frames from any host, form submission, workers and `<base>`. Only the hub's origin may frame the page. The answer also has `Referrer-Policy: no-referrer`, `X-DNS-Prefetch-Control: off` and `Cache-Control: no-store`.
- A request from the page itself to the hub carries no session cookie (the cookie is `SameSite=Lax` and the page's origin is another site), and the API refuses it as cross-site.

The CSP cannot stop a page from navigating its own frame or opening a window to another site, and the browser does not apply it to WebRTC. So a page can send what it shows, and what the user types into it, to a site in a URL. The agent writes the page and can already reach the internet from its tools, so this gives the agent no new access to data, but do not type secrets into a page.

The hub puts a small script at the start of every page that defines `window.hermes`:

- `hermes.send(text)` sends text to the chat now, as the user's message, the same way the message box does: it steers a running turn or queues (with Stop and send now), and nothing is put in the message box. The page stays open and the hub shows `Sent to the chat at 2:31 PM` under the page's bar, so the page's buttons stay usable and the user closes the page when done. A second send while one is in flight is ignored. When the send fails, the hub shows the error with Retry and Copy. The call returns a promise of `{ok, error}`. A click on an element with a `data-hermes-send="<text>"` attribute does the same.
- The message shows in the chat as the user's, with a small `From page: <title>` tag. The text that Hermes receives starts with the line `[Answer from the page "<title>"]` (title on one line, at most 80 characters), then the page's text, so the model knows where it came from.
- `hermes.draft(text)` puts text in the chat's message box, after any text already there, closes the page and shows the chat, for a page that wants the user to edit the text first. A click on an element with a `data-hermes-draft="<text>"` attribute does the same.
- `hermes.copy(text)` copies text. It tries the frame's own copy command, then the hub's clipboard access, and else shows the text selected in a dialog for the user to copy.

The script talks to the hub only over a `MessagePort` that the hub's frame sends to the page on its first load. The hub ignores `postMessage` to its window, so another frame or window cannot speak for the page. When the frame loads a second document (the page followed a link, for example), the hub closes the port and says that the page left; Reload starts it again. A page that leaves before its first load ends is not noticed, and the document it went to gets the port; that document came from the page, so it can do nothing the page could not. A page that is not in the hub's frame (opened on its own, it has no port) cannot send: `hermes.send` and `hermes.draft` copy the text and answer `{ok: false, error}` that says so; opened from a link, the page's address is the hub's own, which asks you to sign in first. While the page is hidden behind the chat, the hub ignores what it sends, and it drops a message of more than 200000 characters.

## Page chat

The Talaria Firefox extension (talaria 0.22.0 and later) opens a small chat from its toolbar button, and moves it to the Firefox sidebar and back. The agent of that chat can read the tabs of that Firefox window. It is the hub's own page in a frame: `GET /pagechat` serves the hub page with the `pagechat` class, which switches `app.js` to the page chat layout (`pagechat.js`). So the page chat uses the same chat, message box, message rendering and meters as the hub, and a hub release changes it without an extension release.

- **Framing.** Only `/pagechat` may be framed, and only by the hub itself and extension pages: `frame-ancestors 'self' moz-extension:`. Every other page keeps `frame-ancestors 'none'`. Firefox gives the frame of an extension with host permission for the hub the hub's first-party cookies, so the hub's sign-in, origin check and CSRF token work there as in the hub (talaria `docs/browser.md` section 6.2). When the session is gone, the page chat asks you to sign in to the hub in a tab, since the sign-in does not run in a frame.
- **Start.** The first message starts the chat: `POST /api/pagechats` with `{"backend_id", "device_id"}`. `device_id` is the computer that runs the extension (talaria reports it to the extension). The chat starts in the sandbox of that computer's backend, else of `backend_id`, and the hub asks the device plugin to make that computer the chat's browser device (`PUT /api/plugins/device/sessions/<id>/browser`). The answer is the new chat with `browser_device`, or `browser_error` when the computer's Firefox is not connected or the plugin is older. The chat runs anyway; the agent then picks a browser device as for any chat.
- **Page chats are chats.** They show in the hub's chat list. Rows of `GET /api/sessions` have `page: true` for chats that the page chat started (kept for each user, with the pins). The page chat's title opens a list of the latest page chats. "Open in the hub" opens the same chat in a tab.
- **The tabs.** Before each message, the page chat asks the extension for the tabs the message covers: every `http` and `https` tab of the window except the hub's own, or only the active tab ("This tab only"), and the active tab's selected text. The extension lets the chat read those tabs for 30 minutes. The page sends them as `page` in the prompt: `{"text", "page": {"scope": "window" or "tab", "tabs": [{"tab_id", "title", "url", "active"}], "selection": {"tab_id", "text"}}}`. The hub checks them (at most <!-- docgen:const pkg=internal/hub name=MaxPageTabs -->`50`<!-- /docgen:const --> tabs with `http` or `https` URLs, a title of at most <!-- docgen:const pkg=internal/hub name=MaxPageTitle -->`200`<!-- /docgen:const --> characters, a selection of at most <!-- docgen:const pkg=internal/hub name=MaxPageSelection -->`4000`<!-- /docgen:const --> characters) and adds a block to the end of the message. The block starts with `[Talaria page chat.`, tells the agent to read a tab with `browser_snapshot` and its `tab_id`, and puts the titles, addresses and selection in an `<untrusted-page-context>` block, since pages control them. The hub page and the Telegram echo show the message without the block.
- **Layout.** A header with the chat's title (it opens the page chat list), new page chat, move to the sidebar or back to the popup, open in the hub, and close in the sidebar; the messages, with tool steps folded into one line; the message box with the scope chip, a "+ selection" chip while text is selected, the model (it opens the hub's model and thinking panel, also before the chat has started), and the one send, stop or steer button; and a row of meters: the context window, the Claude account's 5-hour and weekly windows when it has them, and the chat's tokens in and out. Before the first message the hub reads the backend's default model, its context window and the Claude pool's week from the backend (`GET /api/backends/{backend}/models`, from the dashboard's `/api/model/options` and `/api/model/info`), so a fresh browser profile shows them too, with no tokens used yet. The model of the last page chat shows instead when the backend still offers it. A model or thinking level picked before the first message applies to the chat that message creates.

## Memory

"Memory" in the sidebar opens a page with three tabs for each backend the user may use. A count by it shows memory writes that Hermes waits to have approved. Running chats keep the memory they loaded at their start, so changes apply to new chats.

- **Notes** and **About you** are Hermes's built-in memory, `MEMORY.md` (Hermes's own notes) and `USER.md` (its profile of the user). Each shows its entries with Edit and Delete, a meter of the characters used against the limit from Hermes's config (`memory.memory_char_limit`, default 2,200, and `memory.user_char_limit`, default 1,375), and, when `memory.write_approval` is on, the writes Hermes staged with Approve and Reject. Under "Advanced" are the file path, a switch for `memory.write_approval` and an editor for the whole file. The hub reads and changes them through the talaria device plugin's memory routes (talaria docs/protocol.md section 9.1), which use Hermes's own memory store, so its limits, file lock, threat scan and approval rules hold. The switch uses the dashboard's `PUT /api/config`. A backend whose Hermes has no talaria device plugin with those routes has no Notes tabs.
- On the **Notes** tab, a picker shows "Global notes" (the backend's `MEMORY.md`) or one project's `MEMORY.md` from the project-memory plugin. A project is a git repository, keyed by its normalized remote URL (a mirror on another host attaches as an alias), a repository without a remote keyed by its root commit, or a folder outside git. The picker lists each project by name and identity and shows its aliases and the folders where Hermes saw it, by device. A project's notes have Edit, Delete, Add and the whole-file editor, as the global notes do; they have no approval. The hub reaches the plugin at `/api/plugins/project-memory/` through the same dashboard session, and its own routes are `GET /api/memory/{backend}/projects`, `GET /api/memory/{backend}/projects/{project}/notes` and `POST /api/memory/{backend}/projects/{project}/notes/memory/{op}` with `op` one of `add`, `edit`, `remove` or `replace`. The page address of a project is `#/memory/{backend}/notes/{project}`. A backend whose Hermes has no project-memory plugin has no picker.
- **Learned** lists the facts ("conclusions") Honcho drew from the user's chats, for a backend with `backends[].honcho`. It searches by meaning, sorts newest or oldest first, filters Hermes's view of the user (observer `ai_peer`) or the user's own words (observer `user_peer`), and deletes one or several facts after a confirmation. A fact links to the chat it came from when its Honcho session id is a chat of that backend. Under "Advanced" are the counts, the profile card (Hermes's card of the user, else the user's own), a form that adds a fact as Hermes's view, and an export of every stored copy as JSON. Before it deletes a fact, the hub reads it and checks that it is about `user_peer`. The Honcho API key stays in the hub: browsers never get it.
- Honcho often stores one fact twice, once in each view. The Learned tab shows such a fact once, marked "Both views", and Delete removes every copy. Two copies are one fact when their text is the same after case and runs of white space are ignored; text that differs in any other way, such as punctuation, shows as two facts, so a delete never removes text the user did not see. A paired fact matches both view filters. The counts are of distinct facts, and Advanced also says how many copies Honcho stores. To pair copies and count facts, the hub reads every stored copy for each list and count, at most the newest 10,000. Past that limit, a copy older than the newest 10,000 is not paired, so a delete can leave it behind.
- Honcho marks the kind of each conclusion in its `level` field. Its deriver writes `explicit` facts, taken straight from one message ("From one message"). Its dreams later write `deductive` ("Deduced"), `inductive` ("Pattern") and `contradiction` ("Conflict") conclusions from facts it already has. The Learned tab shows only the dream conclusions at first; "Show all" brings back the facts from single messages. A paired fact shows as condensed when any copy is. A fact added on the page is `explicit`, so after a save the tab turns on "Show all".

The hub checks on every request that the user may use the backend, so a user sees only the memory of the backends they may use. A backend has one `MEMORY.md`, one `USER.md` and one Honcho user, so every user of a shared backend sees and changes the same memory. Give each person their own backend, with `honcho` set to that person's own workspace and a key scoped to it.

The whole-file editor sends the entries it showed with the edited text. Entries Hermes added meanwhile stay; when Hermes changed or removed one of the shown entries meanwhile, the save fails and asks for a reload. The Learned tab shows only conclusions whose observer is `ai_peer` or `user_peer`, so conclusions of other peers in the workspace never show and cannot be deleted from the hub. A fact links to its chat only when Hermes names its Honcho sessions after its own session ids (Honcho `sessionStrategy: per-session` without a peer prefix); with other strategies the link does not show. Honcho errors go to the hub log; users get a short message.

## Search

The search box over the chat list matches chat titles as the user types. From the second character it also searches the messages of every chat on each backend the user may use, and lists the chats with matching messages under "In messages": the title, the date the chat was last used and up to two short excerpts with the matches marked. A click opens the chat at the first matching message, or says that the message is further back than the chat shows.

The hub asks each backend's talaria device plugin (`GET /api/plugins/device/search?q=<text>`, talaria docs/protocol.md section 9.2), which runs Hermes's own full-text search (`SessionDB.search_messages`, FTS5 with Hermes's fallbacks) over user and assistant messages, without the background sources that Hermes's `session_search` tool hides. A match in an earlier part of a chat that Hermes compressed opens the chat that continues it. The search takes Hermes's syntax: words, `"phrases"`, `AND`, `OR`, `NOT` and `prefix*`. Hermes's gateway has no search call, so the search needs a talaria device plugin with that route; a backend without one shows a note under the results. The excerpts are text: the page never renders them as HTML.

## Usage

"Usage" at the foot of the chat list opens a page for one backend and one time range: today, the last 7 or 30 days, this month or the last 90 days. Every section follows that range. Hermes counts its own sections over that many 24-hour periods back from now (today is the last 24 hours, this month is as many days as the date):

- **Tokens by day**, **Chats** and **Models**: the token counters Hermes keeps for each session and each model in its session store, read through the plugin (`GET /api/plugins/device/usage`). Hermes keeps one total per session, not one per call, so a chat counts on the day it was last used. Context is how full a chat's context was in the latest usage event the hub saw for it.
- **API limits**: the rate limits each provider last reported, from the `rate_limit` of the `session.usage` events the hub sees while chats run. Hermes parses only `x-ratelimit-*` headers (`agent/rate_limit_tracker.py`); it does not read Anthropic's own `anthropic-ratelimit-*` headers or any spending limit of an API key, so for Anthropic the section stays empty until Hermes does. Ollama has no API limits; the section shows the tokens per second and seconds per call that Hermes measured in the latest chat of each model. Each hub replica keeps what it saw in memory, since it started.
- **Local GPU**: with `usage.prometheus_url` set to a Prometheus query API that scrapes [ollama-priority-proxy](https://github.com/USA-RedDragon/ollama-priority-proxy)'s metrics, the time in the last 24 hours, 7 days and 30 days that Ollama had a request running (`ollama_priority_proxy_in_flight` above 0, checked each minute), the summed request time of people's and of background requests (`ollama_priority_proxy_upstream_duration_seconds`), and the number of requests. Hermes itself records no request times.
- **Memory backlog**: Honcho's queue for the backend's workspace (`GET /v3/workspaces/<workspace>/queue/status`), for a backend with `backends[].honcho`.
- **Claude Code**: see [Claude Code usage](#claude-code-usage).

### Claude Code usage

The Claude Code panel, under "Subscription accounts", shows the tokens that Claude Code used on the person's own computers and in the Hermes of each backend they may use, for the Usage page's range in days of `claude.time_zone` (default `ui.time_zone`). Computers keep about 35 days of transcripts, so for the last 90 days the panel names the first day it has counts for. It shows the total tokens, the output tokens, the share of input read from the cache, the cost at API prices, tokens per day stacked by group, and a table by account, computer, model or project.

- **Where the numbers come from.** Each computer's `talaria run` reads only the token counts, model, time, account and organization ids, the subagent flag and the project folder's base name from the Claude Code transcripts, never what was said, and sends sums per hour, account, organization, model and project on the device API (`POST /api/device/usage`). In each Hermes pod, `acp-host` counts the same way in each claude-accounts slot directory, and the hub asks it every 5 minutes, and when the panel opens, with a device assertion for the `usage` leg (`GET /usage` on `backends[].acp_url`). talaria's docs/protocol.md section 13 lists exactly what is read and sent. The hub stores the sums per source and hour in `claude_code_usage`, and the accounts each source is signed in as in `claude_code_accounts`.
- **Accounts.** An account is named by the email of the computer's signed-in Claude account, or for a claude-accounts slot by the slot's label. Each slot shows up, with no tokens until it is signed in. A folder that no slot names any more (acp-host labels it with its folder name) and that never signed in is left out. An account that nothing names shows its id and a "Name it" button, which keeps the person's own name for it (`PUT /api/claude-code/accounts/{uuid}/name`, in `claude_account_names`). Sessions that Claude Code wrote before it recorded the account count as "Unknown account". A computer removed in Settings no longer counts: paired again, it sends the same hours under its new id.
- **Cost.** The price of each model comes from the Claude entries of [LiteLLM's price list](https://github.com/BerriAI/litellm/blob/main/model_prices_and_context_window.json), the list ccusage uses, kept in `internal/claudecode/prices.json`. The Update prices workflow refreshes it every week; the hub never fetches it. 1-hour cache writes cost their own rate. It is an estimate: long-context rates and the fast-mode multiplier are not applied, and a model without a price counts as $0 and is named under the table. A subscription does not bill this cost.

## Scheduled

"Scheduled" in the sidebar, with the number of jobs, opens a page with the Hermes cron jobs of every backend the user may use. Times show in `ui.time_zone` (default: the server's time zone, else UTC). "Next 7 days" lists the next run of each job that runs in the coming week. Filters show all jobs, those that need attention (the last run failed or needs a login), active ones or paused ones. A job's row shows its state (a green, red, amber, gray or pulsing dot), its next run, its schedule, where it runs, a badge (Last run failed, Needs login, Result not delivered, Paused, Running) and the result of its last run. "Needs login" uses the same words as the job notices (see [Notifications](#notifications)).

A row opens to the schedule (with its cron expression), where the job runs, its model, its skills, where its results go, its instructions and its 5 latest runs, with Run now (Cancel run while it runs), Pause or Resume, Edit and Delete, which asks first. "Open chat" on a run opens the chat of that run. A run row says only how the run ended (Finished, Running, Stopped, or Failed with the latest run's error), not text from the chat.

The hub reads and changes jobs through the cron routes of the Hermes dashboard on the Webapp listener, with its own dashboard login: `GET /api/cron/jobs`, `GET /api/cron/jobs/<id>/runs`, `POST /api/cron/jobs`, `PUT /api/cron/jobs/<id>`, `POST /api/cron/jobs/<id>/pause`, `resume`, `trigger` and `cancel`, and `DELETE /api/cron/jobs/<id>` (`hermes_cli/web_routers/cron.py`). The run list is Hermes's own: agent runs are the sessions of source `cron` of the job, and runs of script jobs come from the job's output files and `cron/executions.db`. The model list comes from `GET /api/model/options` and `GET /api/model/info`, and Hermes's time zone from `GET /api/config`.

- **Run now.** Hermes runs the job inside the trigger call and answers when the run ends, so the hub keeps the call open in the background, for up to 6 hours. Hermes resumes a paused job when it runs it; the hub pauses it again as soon as Hermes claimed the run.
- **New job and Edit.** Hermes reads every schedule; the page never parses one. While the user types, the hub sets the text on a paused draft job of that user (paused reason `Talaria draft: not saved yet`), and Hermes parses it with its own `parse_schedule`. The draft never runs, the page never shows it, and the hub removes it when the form closes, or on a later list when it is older than an hour. "Next:" shows the next two times of what Hermes made of the text: a cron expression on the wall clock of Hermes's time zone, an interval from now, or the time of a one-shot. A six-field cron expression gets no times until the job is saved. A new job is made paused (from the draft, when there is one); the hub then records who made it (`talaria_owner`) and where its results go (`talaria_results`) on the job and resumes it, and removes it again when Hermes does not resume it. A saved job shows Hermes's own `next_run_at`.
- **Fields.** The form sends only the name, the schedule, the instructions, the model with its provider (empty to follow the chat model) and where the results go. It never sends a script, `no_agent`, `workdir`, `monitor_script`, `monitor_url`, `interpreter`, `base_url` or another field that runs or fetches on the Hermes server. A job that has such a field can only be paused, stopped or deleted from the hub, as the talaria plugin allows from a device session (`CRON_SAFE_ACTIONS`).
- **Runs in.** "Sandbox" on a backend with `devices` and a service device, since the talaria plugin runs the tools of a cron run on the sandbox with `fallback: device` (the hub does not read that setting), else "Hermes server". When the talaria plugin gave the job a computer's Firefox (`$HERMES_HOME/device/browser.json`, read through the dashboard's file download), it adds "Firefox on" and the computer's name. Only a chat can give a job a browser, since the plugin asks the user's OK for it (`browser_use_device` with `job_id`), so the form shows this but cannot change it.
- **Results go to.** Hermes saves the result of a job made in the hub with the run (`deliver: local`); the choice sets how the hub tells the user. "This hub only": no Telegram notice for its runs, also not for a failure; Web Push follows the user's settings. "Telegram, General topic": a notice for each finished run, in General or the private chat, also when the user's "Scheduled jobs" notices are off. "Telegram, its own topic": in a linked group each run's chat gets its own topic (see [A topic for each chat](#a-topic-for-each-chat)), and General gets only its failures; without a linked group it acts as General. A job that a chat made sends its results into that chat until the user picks one of these. Other failure notices follow the user's settings.

The hub checks on every request that the user may use the backend. On a backend that more than one person may use (more than one name in `users`, or any `groups`), a job shows only to the person who made it: the owner that the talaria plugin recorded (`job_owners` in `browser.json`), else the `talaria_owner` the hub recorded. A job whose maker is not known shows to nobody there, and its notices go to every user of the backend as before. On a backend of one person, that person sees every job. The hub acts only on a job's id, though Hermes also takes a name. Every change needs the CSRF token.

## Claude

A backend's Hermes can offer Claude models three ways. Each chat picks one in the model list, like any other model:

- **Subscription accounts, pooled.** The claude-accounts Hermes plugin runs the official `claude` CLI with one Claude account's config folder per slot. Its provider `claude-pool` lists each Claude model once; the model list shows them by name ("Opus 5.5") under "Claude", first. The plugin picks the account for each turn: only signed-in accounts with room in every window that applies (the week, the 5-hour session where the plan has one, and a model's own weekly window such as "Fable week"); a new chat gets the one whose weekly window resets soonest; a chat keeps its account, where its prompt cache is, until that account is at a limit or signs out, and then its next turn moves to the next account by the same rule. When every account is at its limit, the turn fails with "All Claude accounts are at their limit; the first resets Mon 12:00 AM CST" (America/Chicago). The pool never moves to an API key. The plugin also keeps one provider per account, `claude-<slot>`, for chats that picked one before; Hermes's config hides them from the model list.
- **API credits.** One provider per account's API key, `claude-api-<slot>` (such as `claude-api-account1`), from Hermes's `providers:` config. The model list shows their models under "Claude API credits" as "Opus 5.5 (account1 credits)". They are never part of the pool.
- **API key.** Hermes's built-in provider `anthropic`. The hub shows it as "Claude API" in the model list and on the line under the chat title.

Under the model list, a chat on the pool shows the account its next turn runs on and when that account's week resets, such as "Runs on account2 (resets Mon 12:00 AM CST)", or why no account can run it. A chat on an API credit provider shows that it bills that account's monthly API credits.

The hub calls the plugin's routes on the Hermes web server with its dashboard login, as for the device plugin: `GET /api/plugins/claude-accounts/accounts`, for one account `GET .../accounts/{id}/usage`, `GET .../accounts/{id}/status`, `POST`, `GET` and `DELETE .../accounts/{id}/signin` and `POST .../accounts/{id}/signin/code`, and `GET .../pool?session=<chat>&model=<model>` for the pool's account of a chat (the hub's own route is `GET /api/claude/{backend}/pool`). A backend whose Hermes answers 404 has no plugin, and the hub shows none of this for it.

**Line under the chat title.** For a chat whose provider is one of the plugin's accounts (the hub looks the provider up in the account list), or the pool (the account the pool runs it on), the line shows the account's name, the share of the 5-hour session and of the week that it used, and when each resets (only the windows the account's CLI reports; some plans have no 5-hour window, and then the line leaves it out), in `claude.time_zone` (default `ui.time_zone`): for example "5h 12% (resets 3:40 PM CST)". The page reads the accounts at most once a minute, and the chat's account again after each reply. The hub keeps what it read for a minute, or 15 seconds when a reply asks again. An account that is not signed in shows "not signed in", with a note under the title.

**Usage page.** "Subscription accounts" lists each Claude account: its name, the email it is signed in to (or was last signed in to), its plan, whether it is signed in, and each usage window that the account's CLI reports with the share used and the reset time. Claude admins also get Sign in, or Sign in again.

**API credits.** An account whose API key Hermes has (environment variable `ANTHROPIC_API_KEY_<SLOT>`) also shows an estimate of its API credits left, such as "API credits: about $73 of $100 left, resets Dec 1". It is only an estimate. A Max plan includes $100 of API credits a month and an Ultra plan $200; they refresh each billing cycle and do not roll over. No Anthropic API returns the balance, and an individual Console account cannot read Anthropic's cost report, so the plugin takes the plan's credit and subtracts what Hermes spent through the account's `claude-api-<slot>` provider since the cycle started, at Anthropic's list prices. Use of the key outside Hermes is not counted. The cycle starts at midnight America/Chicago on the slot's `api_billing_day` in the plugin's settings (1 to 28, default 1). Hermes records these turns under its `custom` route with no price, so the plugin counts each chat's API turns toward the `claude-api-<slot>` provider the chat is on; a chat that moved between two keys counts toward the last one.

**Sign-in.** The plugin runs `claude auth login` for the account. Sign in starts it (`POST .../signin`; a sign-in that already runs is reused) and opens a dialog. The dialog first names the account: its name, the email it was last signed in as when known, and why it needs a sign-in (its first sign-in, or the login expired or was revoked). Then it shows the link to the Claude sign-in page and a box for the code that page shows. The hub passes the code to the plugin (`POST .../signin/code`) and shows the result: the email the account signed in to, or why it failed. Cancel sign-in stops it (`DELETE .../signin`). The plugin stops the CLI 10 minutes after it started.

**Lost login.** When a turn on a Claude account ends with the plugin's error "Claude Code is installed but has no usable login", or with an upstream 401 (`status 401` or `authentication_failed`), the hub asks the plugin for the account's status. When the account is signed out:

- The chat gets a note that names the account, the email it was last signed in as and why, with Sign in for Claude admins.
- Each Claude admin of the backend gets a "Claude sign-ins" notice on Telegram and Web Push (see [Notifications](#notifications)), at most one per account in 30 minutes. The Web Push notice names the account in the same words and says to open the hub to sign in, with the chat's link; it never carries the sign-in link.
- On Telegram the hub starts the sign-in as that admin (as Sign in on the page does) and sends the admin the sign-in link, in the General topic of their linked group or else in their private chat, such as "Claude (account1), last signed in as alice@example.com". The message asks for a reply (Telegram opens the reply box): sign in on the linked page, then reply to the message with the code. Only the admin the message went to may answer; the bot passes the code to the same sign-in as the page's dialog, deletes the message with the code when it may (in a group the bot needs the right to delete messages), and edits the sign-in message to show the result: "Signed in as" the email, "Sign-in failed" and why, or "Expired" when the sign-in ended first. A code that Claude refuses can be sent again. When the hub cannot start the sign-in, Telegram gets the plain notice instead.

**Security.**

- `claude.admins` lists who may sign the accounts of each backend in, as `user=backend` pairs (environment variable `HUB_CLAUDE_ADMINS`, such as `alice=main`). Empty, the default, is nobody. Only these users see the sign-in controls, and the hub refuses (403) every other user who tries to start, read, answer or cancel a sign-in. The other users of the backend see usage only.
- The sign-in routes need the session's CSRF token and a same-origin request, like the rest of the API.
- The sign-in link goes only in the answer to the admin who asked for it, and on Telegram only to that admin's own chat or group. The account list leaves it out, and chat notes and Web Push notices never carry it.
- The hub passes the code straight to the plugin. It never logs, stores or sends back the code, and it does not log the link. The page clears the code box when it sends the code, and the Telegram bot deletes the code's message.

## ChatGPT

A backend's Hermes can also run chats on a ChatGPT plan, through its own `openai-codex` provider (`hermes auth add openai-codex`). Hermes reads the plan's usage from ChatGPT, the same numbers its own `/usage` shows: the 5-hour session and the week, each with the share used and when it resets.

The hub reads them from Hermes's model options, with its dashboard login (`GET /api/model/options`, the dashboard's twin of the gateway's `model.options`), and never from ChatGPT or with a token of its own. Hermes answers from what it last read and reads ChatGPT again in the background when that is more than 2 minutes old; it leaves the usage out when it has nothing newer than 15 minutes. Then the hub asks once more 3 seconds later, and if Hermes still has nothing, the account shows "Usage not available: Hermes has not read it yet."

- **Usage page.** "Subscription accounts" lists "ChatGPT" after the Claude accounts, with each window's share used and reset time, in `claude.time_zone`. It has no sign-in button: sign in to ChatGPT in Hermes. A Hermes without the claude-accounts plugin still shows it.
- **Line under the chat title.** A chat on `openai-codex` shows "ChatGPT" and the 5-hour and weekly meters, as for a Claude account. The page reads them as it reads the Claude accounts, at most once a minute and again after each reply, so they can be up to 2 minutes behind.
- A Hermes with more than one ChatGPT login in its credential pool reports usage per login; the hub shows "Usage not available" for it.

## Subagent routes

The Subagents picker beside Model and Thinking sets which models the chat's subagents (`delegate_task`) may use. The chat's own model stays the orchestrator. The choices come from the backend's subagent-routes Hermes plugin, which provides the `model_map` delegation backend with the routes of `delegation.backends.model_map.options` in Hermes's config:

- **Auto (model chooses)**: the model picks a route for each subagent by the routes' descriptions.
- **Every subagent on** a route, such as Haiku 5.5: every subagent runs on that route, whatever the model asks for.
- **Ask for help**, such as Opus when stuck: subagents run on the chat's own model, and the model may start one subagent at a time on the stronger route. A second one while the first runs or starts is refused, and so is any other route.
- **No subagents**: every subagent is refused.

The line under the pickers says what the choice means. The choice belongs to the chat and follows it across context compression; the next subagent takes it. Each turn of a chat with a choice tells the model the rule in one line. `/model` in Telegram shows the choice with a button for each one. The hub calls `GET` and `PUT /api/plugins/subagent-routes/sessions/{session}` (`{"choice"}`) with its dashboard login; its own route is `GET` and `PUT /api/sessions/<backend>/<session>/subagents`. A backend whose Hermes answers 404 has no plugin, and the hub shows no picker for it.

## Chat files

For a chat that runs on one of the user's own computers or in the sandbox, "Files" in the chat's header opens a read-only view of the chat's folder:

- **Folder** lists the chat's folder and lets the user go into its folders and up to the computer's root. It shows a text file with syntax colors (up to 1 MB), an image, and offers any file, such as a PDF, as a download. The browser reads every file as a download (`application/octet-stream`, `Content-Disposition: attachment`, `Content-Security-Policy: default-src 'none'; sandbox`) and never as a page.
- **Changes** lists the files the agent wrote in the chat with `write_file` and `patch`, from the tool calls Hermes stored, and, when the folder is in a git repository, what git shows as changed in the folder since the last commit, with its diff.

The hub asks the device plugin (`GET /api/plugins/device/sessions/<session>/tree`, `/files`, `/diff` and `/changes`, talaria docs/protocol.md sections 9 and 9.2). The plugin applies the read rules of file tools to every folder, file and changed path: inside the device's roots and not a credential path, for the path and its real path on the device. It leaves protected entries out of listings and diffs, runs git read-only, and limits a diff to 1 MiB and to the chat's folder. The hub shows the view only for a chat on the user's own computer or the sandbox; a chat on another person's computer or on the Hermes server has none.

## Set up a Hermes backend

The hub needs the Hermes Webapp listener on an address that it can reach, with a password sign-in. On a non-loopback bind, Hermes always requires sign-in. Add this to the backend's Hermes `config.yaml` (the device's `~/.hermes/config.yaml`, or the cluster instance's config) and restart its gateway:

```yaml
webapp:
  enabled: true
  host: 0.0.0.0
  port: 9120
dashboard:
  basic_auth:
    username: hub
    password_hash: "scrypt$..."
    secret: "<32 or more random bytes>"
```

- Make `password_hash` with `plugins.dashboard_auth.basic.hash_password('<password>')` in the Hermes Python environment. The environment variables `HERMES_DASHBOARD_BASIC_AUTH_USERNAME`, `_PASSWORD_HASH`, `_PASSWORD` and `_SECRET` override these keys.
- Set `secret`. Without it, Hermes makes a random key at each start, so each restart signs the hub out (the hub signs in again by itself).
- Open TCP port 9120 only to the hub (on a device: a host firewall rule for the cluster's node addresses or the tailnet; in the cluster: a network policy).
- Put the same user name and password in the hub's `backends[]` entry, with `provider: basic` (the default).

### Context size

Set the context window of a local model in the backend's Hermes `config.yaml`, once for that model:

```yaml
model:
  context_length: 131072
  ollama_num_ctx: 131072
```

- `model.context_length` is the window that Hermes plans for: the readout's total and the point where Hermes summarizes older messages. It also caps the window that Hermes reads from Ollama.
- `model.ollama_num_ctx` is the `num_ctx` that Hermes sends to Ollama with each request. Without it, Hermes asks Ollama for the model's largest window, capped by `model.context_length`.
- Set both to the same value, sized for the GPU's memory. Hermes reads them when it builds a chat's agent. Restart the gateway after a change so that every chat picks it up.

The size is not a per-chat setting on purpose. Ollama loads a model again when a request asks for a different `num_ctx`, so two chats with different sizes on the shared GPU would make Ollama reload the model each time they take turns. The hub has no per-chat choice for API models either: Hermes v0.23.1 has no session-scoped context or compression setting on the gateway. `session.mutate` with operation `model` takes only `model`, `provider`, `confirm` and `reasoning`, and `config.set` takes no `model.context_length` or `compression.*` key.

When a chat switches to another model, Hermes drops `model.context_length` from that chat's settings and takes the new model's window from its model data. To pin the window of another local model, give it a `context_length` under its name in the `models` of its `custom_providers` entry.

## Set up Authentik

1. Create an OAuth2/OpenID provider: client type confidential, redirect URI `https://<public host>/auth/callback` (strict), signing key set, scopes `openid`, `profile` and `email`. Authentik's default `profile` scope mapping sends `preferred_username` and `groups`.
2. Create an application with slug `talaria-hub` that uses the provider. The issuer is then `https://<authentik host>/application/o/talaria-hub/`.
3. Bind the users or groups that may log in to the application.
4. Keep the provider's subject mode at "Based on the User's hashed ID" (the default). Put each user's `sub` in the hub's `users[]`; the values belong in the deployment config, not in this repository.
5. Give the hub `oidc.issuer_url`, `oidc.client_id` and `oidc.client_secret`.

## Telegram

Set `telegram.enabled`, `telegram.token` and `http.public_url`. A Telegram user sends `/link` to the bot and gets a link to `/link/telegram?token=...`. That page needs a hub login and asks the user to confirm; only the confirmation (a POST with the CSRF token) links the account. A link token is valid for <!-- docgen:const pkg=internal/store name=LinkTokenTTL -->`10m0s`<!-- /docgen:const --> and works once.

`/status` shows the attached chat's model and how full its context is, such as `Context: 41k / 131k (31%)`, from the same usage figures as the page. `/model` shows the chat's model with a button for each model it can switch to, named by its group and name as the hub's model list shows them (such as `Claude: Opus 5.5`; up to <!-- docgen:const pkg=internal/telegram name=maxModelButtons -->`24`<!-- /docgen:const -->), and `/model NAME` or `/model provider/NAME` switches directly, with the model's ID as NAME. When Hermes asks to confirm a model, the bot shows its reason and a "Use it anyway" button. On a backend with the subagent-routes plugin, `/model` also shows the chat's Subagents choice and what it means, with a button for each choice (see [Subagent routes](#subagent-routes)). `/bg TEXT` runs a prompt in the background, as on the page (see [Activity](#activity)), and the bot sends its answer to the chat when it is done.

`/prompts` shows a button for each of the user's saved prompts (up to <!-- docgen:const pkg=internal/telegram name=maxPromptButtons -->`50`<!-- /docgen:const -->). A press sends the prompt's text as it is now in a code block, which Telegram can copy with one tap, split over several messages when it is longer than one message. The hub does not answer inline queries, so the bot does not put the text in the message box: Telegram's `switch_inline_query_current_chat` needs inline mode and takes at most 256 characters.

**Command menu.** When it starts, the bot sets its command menu (`setMyCommands`) for each place: private chats get `/new`, `/stop`, `/model`, `/bg`, `/status`, `/prompts`, `/sessions`, `/backends`, `/devices`, `/where`, `/move` (the last three with computers on), `/link`, `/unlink` and `/help`; groups get `/link` and `/help`; each linked group gets the commands of a linked group. `/device` and `/computers` work as `/devices`.

**Private chats stream.** In a private chat (with `telegram.drafts`, on by default), each turn streams into a draft (`sendMessageDraft`, Bot API 9.3): a message that Telegram shows while it is written and that goes away when the bot sends the real one. Until the reply starts, the draft shows the status line described below, with its time. Then it shows only the reply as Hermes writes it: Telegram animates a draft that only grows, but redraws all of it when its start changes, and the status line's time changes every second. The bot sends the draft at most once every <!-- docgen:const pkg=internal/telegram name=draftGap -->`1s`<!-- /docgen:const -->, and again every <!-- docgen:const pkg=internal/telegram name=draftKeep -->`10s`<!-- /docgen:const --> when nothing changed, because Telegram drops a draft after about 30 seconds. The turn's status line is then sent once, as "Working…" with its Steps button, and edited only when the turn ends. Telegram takes drafts only in private chats (also in their topics), so in a group the bot edits the status line as below. When Telegram refuses a draft, the bot falls back to editing the status line for that chat.

Each turn gets one status line: a single message that the bot edits in place, at most once every `telegram.edit_interval`. While Hermes works it is one line: what runs now ("Thinking…", "Writing…" while the reply streams, or "Running terminal `go test ./...`"), the number of steps so far, the time and the turn's tokens, such as "Running terminal `go test ./...` · 5 steps · 1m 12s · 14k in, 1k out". When nothing else changes it, the bot edits the line every <!-- docgen:const pkg=internal/telegram name=statusTick -->`10s`<!-- /docgen:const --> so its time keeps going. The time counts from when the hub saw the turn start, also when the chat attached later. Telegram folds an expandable quote again each time its message is edited, so the running line has no quote. Its Steps button sends a new message with the steps and the end of the model's thinking so far in a quote; the bot never edits that message, so a quote opened there stays open. When the turn ends the bot edits the status line one last time, and then never again: it says what the turn did, such as "Worked for 2m 5s: ran 3 commands, edited 1 file · 31k in, 3k out", with all the steps and the end of the thinking in a quote, and the Steps button goes away. The token counts are the turn's, as on the page (see [Activity](#activity)); they show from the turn's first usage event, and only the output count shows when the hub cannot tell the input. With `telegram.steps: collapsed` (the default) the quotes are folded and open on a tap; `expanded` shows them open; `off` leaves out the quote and the Steps button. The reply is always a message of its own, and the bot's messages never show link previews.

**Edit budget.** Telegram limits how often a bot may send to a chat: about once a second in a private chat and 20 times a minute in a group, which all topics of the group share (Bot FAQ). Edits count too: Telegram answers too many of them with 429. The bot spaces the edits that can wait, the status lines and to-do lists, so that all topics of a chat together edit at most once every <!-- docgen:const pkg=internal/telegram name=privateEditGap -->`1s`<!-- /docgen:const --> in a private chat and every <!-- docgen:const pkg=internal/telegram name=groupEditGap -->`3s`<!-- /docgen:const --> in a group. Replies, prompts and other messages that must go are never held back, but the next edit waits after them.

**Reactions and typing.** The bot reacts to the message that started a turn: 👀 when Hermes picks it up, 🙏 while an approval or a question waits for you, 👍 when the turn ends well, 👌 when it was stopped and 👎 when it failed. Each reaction replaces the one before. Telegram lets a bot react only with its fixed set of emoji, which has no ✅, ⚠️ or ❌. For a turn started elsewhere, the reactions go on the bot's copy of its prompt. In a group that does not allow those reactions the bot stops trying. While a turn runs, the chat or topic shows that the bot is typing (`sendChatAction`), renewed every <!-- docgen:const pkg=internal/telegram name=typingGap -->`4s`<!-- /docgen:const -->.

**To-do list.** When Hermes writes or updates its to-do list (the `todo` tool), the bot shows it as a message with ☐ for each item to do, ☐ in bold for the one in progress, ☑ for done and ☒ for cancelled, and edits that message as items finish. Each turn starts a new message. Telegram's own checklists (`sendChecklist`) can be sent only for a business account, which this bot is not.

**Approvals and questions.** An approval ("Needs you") shows the command and has a button for each choice that Hermes offers: Once, This chat, Always and Deny. A question has a button for each of its choices (up to 10; more get numbered buttons), Other answer and Skip, and a question with several picks toggles its choices and has Send. To give an answer of your own, reply to the question's message (Telegram's Reply), or press Other answer, which asks for a reply. A question without choices asks for a reply at once (Telegram opens the reply box); a reply of `/skip` skips it. A message that is not a reply to a question goes to the chat as usual. When a prompt is answered, the bot edits its message: it shows what became of it ("Approved once", "Answered: main", "Skipped") and who answered, and the buttons go away. An approval that is answered somewhere else shows the choice and where it was given, such as "Allowed always (in the hub)", "Denied (in Telegram)" or "Allowed once (on laptop)" for a paired device. Hermes does not say which choice answered an approval, so the hub records the answers that pass through it: on the page, in Telegram and from paired devices (`approval.respond`, or the answer to the gateway's `approval` request). For an approval answered in an app that talks to Hermes directly, the message first shows "Answered elsewhere", and then "Allowed (in another app)" or "Denied (in another app)" when the tool call that asked ends: allowed when it ran, denied when its result says the user denied it. The hub cannot tell the scope (once, this chat or always) of such an answer, so it does not show one. It links the approval to its tool call only when that is certain: the one running terminal call with the approval's command, or else the only running call, when it is a tool that asks while it runs (terminal, write_file, patch, computer_use) and no subagent runs. It does not use execute_code, whose own terminal and file calls ask without a tool call of their own, nor an approval of a plugin rule, which comes before its call starts. When two apps answer an approval, Hermes takes the first answer, and so does the hub. A question that is answered somewhere else shows "Answered elsewhere"; a prompt that Hermes cancels shows "Cancelled"; one whose time runs out (Hermes's `timeout_s`) shows "Expired". The page's approval cards show the same outcome. The buttons of an old message then answer "This request is no longer pending."

Images that one reply names go as one album (`sendMediaGroup`) of up to <!-- docgen:const pkg=internal/telegram name=maxAlbum -->`10`<!-- /docgen:const --> images and <!-- docgen:const pkg=internal/telegram name=maxAlbumBytes -->`41943040`<!-- /docgen:const --> bytes, after the reply's other files. When Telegram refuses the album, the bot sends the images one by one.

A photo, an image or other file, a video or a voice note sent to the bot goes to the chat like an attachment on the page, with its caption as the message. A PDF gets its text and first pages read as on the page; the bot cannot pick its pages. The photos and files of one album go as one message. Telegram lets bots download files of up to 20 MB, so the bot answers a larger one with a note instead.

Telegram lets only one process long-poll a bot token. With `store.driver: postgres`, the replicas elect one leader with a PostgreSQL session advisory lock, held on a connection of its own. Only the leader polls. The other replicas try to take the lock every `telegram.leader_retry` (default 2s), so one of them takes over a few seconds after the leader stops. If the leader dies without closing its connection, PostgreSQL frees the lock when its TCP keepalive gives up, after about 15 seconds. The leader checks its lock every 2 seconds and stops polling when the check fails. With SQLite there is one replica, and it always leads.

The bot streams each chat's session through a subscription in the leader's own process. Hermes sends every session event to every subscriber, so a turn that a page started on another replica still reaches the chat. The store keeps each chat's session and the bot's update offset, so a new leader attaches every chat again and carries on from the last update the old leader finished. A leader that loses its lock stops after the update it is handling. The bot sends each message under a submission ID derived from its Telegram update, so if a new leader handles an update again, Hermes still runs the message once. If a turn runs while the leader changes, the new leader can repeat that turn's progress messages in the chat.

A chat can ask Hermes to schedule a task (Hermes cron, `cronjob_manage`). Hermes writes each result into the chat it was scheduled from as a note, not as a turn. The page shows the note as a result card, and the bot sends it to every Telegram chat attached to that session. A chat started on the page sends its results only to the page until a Telegram chat attaches to it.

### A topic for each chat

Each hub chat can get its own topic, so replies of different chats never mix: in the private chat with the bot, or in a group that the person links.

**In the private chat.** Turn on topic mode for the bot in the @BotFather Mini App (the bot reads `has_topics_enabled` from `getMe` every <!-- docgen:const pkg=internal/telegram name=meEvery -->`1m0s`<!-- /docgen:const -->). Then the next message of a person without a linked group turns topics on in their private chat with the bot, and everything below works there as in a linked group: the bot makes a topic for each chat, the main chat takes the place of General (a message there starts a new chat in a new topic, and notices come there), and "Open the topic" links have the form `https://t.me/<bot>/<topic>`, which opens the topic only for that person. Telegram cannot close a topic of a private chat, so archiving a chat adds " · archived" to its topic's name instead, and taking it out of the archive takes that off again. When topics are turned off in @BotFather again, the private chat goes back to following one hub chat at a time; its topics stay in Telegram. When the Telegram account is linked to another hub user, its private chat stops showing the old user's chats and notices. A person's other linked Telegram accounts keep getting notices in their private chats. Without topics, each person talks to the bot in one private chat, which follows one hub chat at a time.

**In a group.** A person can instead link a private group with Topics to the bot. Then each of their hub chats gets its own topic in that group. Each hub user links their own group, and a linked group takes the place of topics in the private chat; `/unlink` in the group, or in the private chat, unlinks it.

To set it up:

1. Link your Telegram account first: send any message to the bot in a private chat and follow the link.
2. In Telegram, make a new group. Add the bot to it.
3. Open the group's settings and turn on Topics. (This turns the group into a supergroup. Do this before step 5: the group's ID changes.)
4. Make the bot an admin of the group, with the rights to manage topics and to delete messages (it deletes the topics of deleted chats).
5. In the group, send `/link`. The bot checks that Topics are on and that it may manage topics, and links the group to the hub user of the Telegram account that sent `/link`. Only a linked Telegram account can link a group, and only to its own hub user. Linking a new group replaces the person's earlier group, and topics in the private chat.

How it works:

- **Topics.** Every `telegram.topic_sync` (default 20s) the bot lists the person's chats. A chat that started after the link, or one that runs, gets a topic named after the chat's title, plus where it runs when that is a computer or the sandbox, or "scheduled" for a scheduled job's chat, such as "Fix CI · laptop". When the title changes, the topic's name follows. Archived chats get no topic, and neither do the conversations that Hermes holds itself on a messaging platform (they may have other people in them), its subagents or its `/bg` prompts (`bg_...` sessions). The store keeps each group and its topics, so a new leader carries on.
- **Talking.** A message in General starts a new chat in a new topic, named after the message's first line until Hermes gives the chat a title; the bot copies the message into the topic and answers in General with a button that opens it. `/new [backend]` and `/new NAME [folder]` start a chat in a new topic too. A message in a topic goes to that topic's chat. A topic that someone made by hand gets a new chat, named after the topic. `/stop`, `/status`, `/where` and `/move` act on the topic's chat. The bot ignores messages from anyone in the group whose Telegram account is not linked to the group's hub user.
- **Following.** The bot follows a topic's chat while it runs, also when it started on the page, in an editor or in a scheduled job, and while someone talks in the topic. It shows the turn that runs when it starts following, not the turns before, and the approvals and questions that still wait.
- **Prompts from elsewhere.** When a turn starts from anywhere but this topic, the bot first posts the prompt that started it, with where it came from: "You, in the hub:", "You, in the terminal:", "You, in an editor:", "You, in Telegram:" (another chat with the bot) or "You, in another app:". It names the prompt's attachments and cuts a prompt longer than <!-- docgen:const pkg=internal/telegram name=echoLen -->`1000`<!-- /docgen:const --> characters with "(…, full text in the hub)". An agent message shows as "Agent message from …". The bot tells its own prompts by their submission IDs, which name the chat and topic they were sent in; the hub's own submission IDs start with `hub:`. When the bot attaches to a turn that already runs, it takes the prompt from the chat's transcript. The private chat with the bot does the same. It stops following a chat that has not run and showed no prompt for <!-- docgen:const pkg=internal/telegram name=topicIdle -->`15m0s`<!-- /docgen:const -->.
- **General.** Notices go to General instead of the private chat: scheduled job results, failures, long tasks that ended, and reminders of prompts that still wait, each with a button that opens the chat's topic when it has one. An approval or question of a chat with a topic shows in that topic only, until its reminder.
- **Deleted topics.** When Telegram refuses a message because its topic was deleted or closed, the bot forgets the topic. The chat gets a new topic when it runs again, at least <!-- docgen:const pkg=internal/telegram name=topicIdle -->`15m0s`<!-- /docgen:const --> later.
- **Deleted and archived chats.** When a chat is deleted, in the hub, in Hermes or by an agent, the bot deletes its topic (`deleteForumTopic`) and forgets it. It learns of a delete from the chat's stream when it follows the chat, and otherwise when it checks the topics: when it starts and every <!-- docgen:const pkg=internal/telegram name=reconcileEvery -->`5m0s`<!-- /docgen:const --> after, it asks the backend (`session.info`) about each topic whose chat is not in the chat list, and deletes the topic only when the backend says the chat does not exist; a backend it cannot reach deletes nothing. Archiving a chat closes its topic (`closeForumTopic`), and taking it out of the archive opens it again. A topic that Telegram says is gone is forgotten. When the bot lacks the rights, it says once in General that it needs "Manage Topics" and "Delete Messages". It never closes or deletes General.
- `/unlink` in the group stops all of this. `/help` in the group lists the commands.

The bot needs to be an admin to see every message in the group (with Telegram's privacy mode, the default, a bot that is not an admin sees only commands and replies to its own messages) and to make and rename topics. Every member of the group sees each topic, so keep the group to yourself.

## Notifications

The hub tells each person on their phone when their Hermes needs them or is done, without a hub page open. A notice goes to the person's linked Telegram chat (when `telegram.enabled` and they linked Telegram) and to each browser where they turned on notifications (Web Push, with `notify.vapid_private_key`). These events notify:

| Event | Default | When |
|-------|---------|------|
| Approvals | on | Hermes asks before it runs something (`approval.request`) |
| Questions | on | Hermes asks the person to choose or answer (`clarify.request`) |
| Failures | on | A turn ends with an error, a scheduled job fails or cannot deliver its result, or an unattended run could not use a tool that needs the person |
| Long tasks done | off | A reply that ran for <!-- docgen:const pkg=internal/service name=longTurn -->`2m0s`<!-- /docgen:const --> or more is ready |
| Scheduled jobs | off | A scheduled job (Hermes cron) finished |
| Claude sign-ins | on | A Claude account that a chat uses lost its login (only for the backend's Claude admins, see [Claude](#claude)) |

Each person picks the events, the channels and quiet hours under Settings, Notifications on the page. During quiet hours the hub sends nothing; an approval or question that still waits afterwards gets its reminder then. "Send a test" sends one test notice to each channel, at most once a minute.

What the hub watches:

- **Chats that someone follows.** Every replica reads the approvals and questions of the sessions that it follows for a page or a Telegram chat.
- **Chats nobody has open.** One replica (the holder of the `notify` leader lock, as for the Telegram bot) lists each backend's live sessions every `notify.watch_interval` (default 15s) and follows each one that runs until it stops, so it sees the approvals and questions of a chat that VS Code, the terminal or a scheduled job started. A prompt that was raised before the hub followed the chat comes from the session's snapshot.
- **Scheduled jobs.** The same replica reads each backend's `/api/cron/jobs` through the Hermes web server every `notify.job_interval` (default 1m) and sends a notice for each run that it had not seen: done, failed, or result not delivered. A failure whose error names a login (such as "log in", "401" or "unauthorized") says that the job needs the person to sign in again. The Telegram notice quotes up to 300 characters of the error, with long runs of token characters (24 or more, as in API keys) replaced by `[hidden]`. The first read of a job only records its last run.
- **Unattended runs.** Hermes does not ask anyone in a scheduled job or a one-shot query. The talaria device plugin's browser tools refuse a step that needs an approval in such a run at once (talaria `docs/browser.md` section 7.3), and the hub does not change that. When a refusal shows in a chat that the hub follows (a tool result with both "<tool> was not run:" and "no user is present in this run"), the person gets a failure notice that names the tool and says to approve it once with Always.

Who gets a notice: each hub user who may use the backend (`backends[].users`, or `backends[].groups` with the groups of their last login). The hub skips a person who has that chat open on a visible page (the page reports this every 45 seconds; it counts for 90 seconds), and on Telegram a person who has a Telegram chat attached to that session, since that chat shows the prompt already. With a linked group, a chat that has a topic gets its approvals and questions only in that topic, and its other notices in General. The store keeps each notice once per person, so two replicas, or a reconnect that replays events, send it once. A person gets at most 20 notices in 10 minutes; the rest are dropped and logged, and get no reminder.

**Reminder.** An approval or question that still waits after `notify.remind_after` (default 5 minutes) gets one reminder. While the person looks at that chat, during quiet hours, or while they are over the limit above, the hub puts the reminder off and tries again later. The hub asks Hermes first whether the prompt still waits. A prompt older than <!-- docgen:const pkg=internal/notify name=maxReminderAge -->`12h0m0s`<!-- /docgen:const --> gets no reminder.

**Telegram.** A prompt in a chat attached to Telegram, or in a chat's topic, shows with its buttons, as described in [Telegram](#telegram). A notice for a chat that no Telegram chat or topic shows goes to the General topic of the person's linked group, or to the main chat of their private chat with topics, or else to each private chat linked to that person, with the same buttons and an "Open in the hub" link. Only that person may press them or answer them with a reply, and only on the message the hub sent; the hub then answers with that person's access, so a press on a chat they may no longer use fails. In an attached chat, anyone linked who may use the backend may answer, and each button works only on its own message, under a random key. In a linked group only the group's own person may. Buttons of older hubs (`ap:` data) do nothing. When the prompt gets its answer elsewhere, is cancelled or expires, the bot edits the notice to say so, with the outcome of an approval as in an attached chat, and the buttons go away. With two replicas, one of them shows an outcome that the hub works out later. Button data holds only a random ID, never the prompt. The bot keeps what it needs to route replies and show outcomes in memory for a day; after the bot restarts, a reply to an older question goes to the chat as a message.

**Web Push.** The page offers "Turn on for this device" when the hub has a VAPID key. The hub stores each browser's subscription for the signed-in person (at most <!-- docgen:const pkg=internal/web name=maxPushSubscriptions -->`10`<!-- /docgen:const --> each), only from a push service it knows (Google FCM, Mozilla, Apple, Microsoft WNS), so a subscription cannot make the hub send requests to other hosts. A Chromium build without Google API keys (the Arch and Debian packages) subscribes on `jmt17.google.com`, which does not deliver to it; the hub refuses that subscription and the page says to use Google Chrome, Firefox or a Chromium build with Google API keys. Subscribe and remove need the session's CSRF token and a same-origin request, like the rest of the API. A push message carries only the event kind, a fixed title such as "Hermes needs your approval", the backend's name and the address of the chat; never the chat's title, the command or the question. A click opens the hub at that chat, behind the normal login. Logging out on the page ends that browser's subscription, and a page that finds a subscription of another person (whose login ended without a logout) ends it too. A subscription moves to another person only when the browser sends the same keys, which only it has. The hub never logs an endpoint. A subscription the push service reports gone (404 or 410) is deleted.

- Android: Chrome and Firefox show notifications from the browser or from the installed app.
- iPhone and iPad: Safari shows Web Push notifications only for a web app on the Home Screen (iOS 16.4 or later). Open the hub in Safari, tap Share, then Add to Home Screen, open it from there, and turn notifications on in Settings.
- Desktop browsers work too.

**Install.** The hub is a progressive web app: `/manifest.webmanifest`, icons in `/static/`, and a service worker (`/sw.js`). The service worker caches only an offline page and its icon. It never caches the hub's pages, API answers or event streams, which need the login. Without a network, the app shows the offline page.

To turn on Web Push, make a key once and keep it; a new key ends every browser's subscription:

```sh
openssl ecparam -name prime256v1 -genkey -noout | openssl pkcs8 -topk8 -nocrypt
```

Put the PEM in `notify.vapid_private_key` (environment variable `HUB_NOTIFY_VAPID_PRIVATE_KEY`) or a file named by `notify.vapid_private_key_file`. `notify.vapid_subject` defaults to `http.public_url` when that is `https`. With an `http` public URL (a localhost or LAN install) and no subject, the hub logs a warning and runs without Web Push; set `notify.vapid_subject` to a `mailto:` or `https:` URL to turn it on. The hub logs the public key at startup. The hub needs outbound HTTPS to the push services (`fcm.googleapis.com`, `updates.push.services.mozilla.com`, `web.push.apple.com` and `*.push.apple.com`, `*.notify.windows.com`); a network policy that limits egress must allow them. A notice's link opens the hub at `http.public_url`, so the phone must reach that address.

## Devices

With `device.enabled` the hub is the server side of [talaria](https://github.com/USA-RedDragon/talaria) (called hermes-device before its release 0.19.0), as its `docs/protocol.md` describes. The hub imports that module's `protocol` and `assertion` packages for the wire names and the hub assertion.

- **Pairing.** `talaria setup` (or `talaria login`) calls `POST /api/device/pair` and shows a code and the link `<http.public_url>/device/pair`. The user signs in there, types the code, checks the computer's name, system, address and request time, names it and confirms. The code never comes from the link, so a link someone else sends cannot pair their computer with this user. The device then gets its token from `POST /api/device/pair/token`, once. The hub keeps only the SHA-256 of the token. The hub limits pairing requests per address and wrong codes per user (10 in 15 minutes).
- **Backend.** Each device is pinned to one backend at pairing: one with `backends[].devices: true` that the user may use. On every request and every WebSocket upgrade, and again every `device.recheck_interval` while a connection is open, the hub checks the token, that the device is not revoked and that its user may still use the backend.
- **Legs.** `/api/device/exec` goes to the device plugin on the gateway listener (`/api/plugins/device/ws`) and `/api/device/acp` goes to the backend's acp-host (`backends[].acp_url` + `/acp`). For each upgrade the hub signs a new Ed25519 assertion (header `X-Hermes-Device-Assertion`, valid 30 seconds, with a random nonce). The exec leg copies messages unchanged both ways; the ACP leg follows the rules below. `/api/device/gateway` goes to the gateway's `/api/ws` with the hub's own dashboard login. The hub pings every hop every 25 seconds and closes a hop that gives no pong in 15 seconds with 4408.
- **Browser control.** talaria can let the agent use the user's Firefox. Its messages ride the exec leg, which the hub copies unchanged. The browser has no sign-in of its own: the device authorizes it, as it does commands. The extension talks only to the local daemon, whose socket only the same OS user can reach, and the daemon is paired to its owner here. The plugin sends browser requests only on the exec leg of a chat's browser device, which must belong to the chat's hub user (the plugin reads each device's user from the hub's signed assertion), and a chat is bound to a computer only by that computer, by its owner here, or by the plugin's `/device` command, which refuses another hub user's computer, so browser requests reach only the user's own computers. The hub does not check browser requests itself, as it does not check commands.
- **Gateway leg rules.** A device token is not operator access to the backend. The hub reads every JSON-RPC message on the gateway leg and applies the rules itself. `session.create` runs in the plugin's placeholder directory with the device directory as its row cwd, and its answer waits until the session is bound to the device; a failed bind deletes the session again. A retry with the same `request_id` gets the same session without a second bind. Before it binds, the hub asks the plugin how it resolves the new session, so a create that returns an existing session of another device is refused, not bound; after a failed bind it deletes only a session that resolves to no device with none in its lineage ever bound. Every request that names a `session_id` needs that session bound to this device (through its lineage), and every `session.resume` is checked on its answer. A resume needs a non-empty `session_id`: one by `title` or `latest` is refused, since the gateway would attach the session before the hub could check it. The hub lets through only an allowlist (`gatewayRules` in `internal/device/rpc.go`): the methods the Hermes Ink TUI and classic CLI send for chatting. It refuses the other methods they send, with the reason in the error message (`<method> is not available through talaria: <reason>`): those that run programs or read or write files in the pod (such as `shell.exec`, `process.*`, `reload.mcp`, `session.save`, `paste.collapse`, `rollback.*`), change the whole profile, its credentials or its account (`tools.configure`, `skills.manage`, `model.save_key`, `connectors.*`, `billing.*`), use the pod's audio (`voice.*`, `wake.*`), legacy methods the gateway refuses on the hub's connection anyway, and every method no client sends. It refuses `delegation.status`, `spawn_tree.list` and `spawn_tree.load`, which read every session's subagents and spawn trees. `image.render` (the TUI's inline image previews) passes only when the backend's `runtime.describe` lists `image-render-confined-v1`, which a Hermes with `security.image_render_paths` set reports (from hermes-patches), and only with the params `path`, `cols`, `rows`, `graphics` and `terminal`; otherwise it is refused, since it would read a file at any path in the pod. The hub reads the capabilities once per leg. `client.capabilities` passes only with the single param `server_requests` (true or false): the TUI sends it so the gateway sends it approvals and questions, which the gateway otherwise fails at once for a WebSocket client. Other capabilities, such as `desktop_local`, are refused. In the answers of `session.list`, `session.active_list` and `session.most_recent` it keeps only the device's own sessions (bound to it through their lineage); a session whose binding it cannot read is left out. It refuses these params: `title`, `base_url`, `api_key` and `accept_hooks` on `session.create` (an existing session, the profile's key sent to a host the device picks, profile-wide hook consent), `cwd` and the `project` key on `config.get` (git in a pod directory), `api_key` on `session.resume`, `staged_upload` on `file.attach` (a browser upload in the pod), and `picker`, `workspace`, `title` and `include_hidden` on `session.list` (the first prompt and last reply of every chat of the backend, chats by another device's folder, a chat by its title, hidden chats) unless the gateway scopes the list to the device: when the backend's `runtime.describe` lists `session-list-audience-v1` (from hermes-patches) and a list with the audience `hermes-device:<device id>` is not refused (the device plugin judges that audience), the hub sets that audience on every `session.list`, replacing any the device sent, and lets those params through. It drops `cwd_explicit` from a create and `refresh` from `model.options`, clamps the sizes of `learning.frames` and `pet.cells`, and refuses a `request_id` that starts with `hermes-hub-`. A device message with no `method` goes to the gateway only as an answer to a gateway request (a string `srq-` id and exactly one of `result` and `error`), rebuilt from those members. It also refuses `session.mutate` operations other than rename, archive, sidebar, model, reasoning, workspace, edit_policy, delete, rewind, reset, branch and compress, requests with any non-null `profile`, `config.set` keys that change the profile (only `busy`, `verbose`, `show_reasoning`, `service_tier`, `fast`, `yolo` without `scope`, and `reasoning` with an exact effort or `reset` in session scope pass), and slash commands outside a short list of session commands (`SlashCommands` in `internal/device/rpc.go`), or with an argument that Hermes reads as `--global` (quoted, upper case or with a Unicode dash too). The same list applies to a `prompt.submit`, `prompt.replace_queued`, `session.steer`, `session.redirect` or `prompt.btw` text that Hermes would read as a slash command (after leading whitespace and `@file:`-style lines, `/cmd@bot` too, aliases counted as their command). `/usage` takes no argument (`/usage reset` redeems an account credit). A `/model` through `slash.exec` or `command.dispatch` gets `--session` put first, where no value flag can take it, and one typed as text is refused: otherwise Hermes may write the pick to the profile's config. When the hub refuses a create's answer, it detaches the subscription the gateway opened with it. The hub forwards each device request under an id of its own and gives the answer the device's id back.
- **ACP leg rules.** The hub reads every JSON-RPC message on the ACP leg (one per WebSocket message) and does not rely on acp-host's checks alone. A device may send `initialize`, `authenticate`, `session/new`, `session/list`, `session/load`, `session/resume`, `session/fork`, `session/prompt`, `session/set_mode`, `session/set_model` and `session/set_config_option` as requests and `session/cancel` as a notification; other requests get `-32601` (reason `hermes_device_denied`) and other notifications are dropped. Each method's params may have only the members the ACP SDK (v0.9.0) defines for it, by alias or field name; any other member, `_meta` above all, is refused with `-32602`, as is a `field_meta` member at any depth: the SDK merges a top-level `_meta` into the handler's arguments, where it would replace the session id or cwd the hub checked. Every one of these except `initialize`, `authenticate`, `session/new` and `session/list` must name its session in `sessionId` or `session_id` (both are checked when both are sent), and the session must be bound to this device, through its lineage, or have been created by `session/new` or `session/fork` on this leg and not bound to another device since. Otherwise the answer is `-32602` with reason `hermes_device_other_device` or `hermes_device_not_bound`. As acp-host does, the hub sets `cwd` to the plugin's placeholder, sets `mcpServers` to `[]` and removes `mcp_servers` on new, load, resume and fork, replaces `resource_link` prompt blocks with a text note, refuses a prompt with any text that is a slash command outside the gateway leg's allowlist (hermes acp sends those to the gateway as `slash.exec` over its own connection), except `/discard` and `/tools`, which hermes acp answers for the session itself (`/discard <id>` clears a turn lost in a gateway restart, which blocks every later prompt of the session), and drops the sessions bound to another device from `session/list` answers (it keeps the sessions bound to this device and those with no binding, which acp-host lists only when they were never bound; none when the bindings cannot be read). From acp-host, the hub relays `session/update`, `session/request_permission` and `elicitation/create`, and answers any other agent request (such as `fs/read_text_file` or `terminal/*`) with `-32601` itself. The hub forwards each device request under an id of its own and drops answers to ids it did not send.
- **Sandbox devices.** `backends[].service_devices` lists devices the hub knows from its config, such as each user's sandbox pod running `talaria run`. They sign in with their configured token (the hub keeps only its SHA-256), are pinned to their backend, and may use only the exec leg and whoami: the gateway leg, the ACP leg and the bind API answer 403. Users who may use the backend see them in Settings as Sandbox, with whether each is online; they cannot remove them there.
- **Bind API.** `PUT` and `DELETE /api/device/sessions/{id}/binding` go to the plugin with the token's device id. A device can bind sessions only to itself and unbind only its own bindings. Before a bind the hub asks the plugin how it resolves the session through its lineage, and forwards the bind only when the session resolves to this device, or to no device with no session in its lineage ever bound. It answers `409` `bound_to_other_device` for a session that resolves to another device, including one that only inherits that binding, and `409` `was_bound` for one that was bound before and is not now, or whose lineage the plugin cannot read, unless a leg of the same hub replica created the session for this device in the last hour (a branch child or an ACP session whose lineage row is not written yet). So a device that unbinds its own session cannot bind it again.
- **Chats on a computer.** The arrow next to "+" lists the sandbox and the user's computers; offline ones are off. A computer (a paired device, not a sandbox) opens a browser of the folders in its roots through the plugin's dirs route, with the recent folders of that computer first (the hub keeps the last 8 per computer). The hub starts the session as the gateway leg does: `session.create` in the plugin's placeholder with the device directory as its row cwd, then the bind, before it answers, so no prompt reaches the session unbound. A failed bind deletes the session again. A plain New chat does not change: it runs where the plugin's fallback puts it, such as the sandbox.
- **Where a chat runs.** The chat list and the line under the chat title show the computer and folder of each chat, or Sandbox, and whether that computer is online. The hub reads `GET /bindings` once per backend and asks `GET /sessions/{id}/binding` only for chats without a binding of their own (such as a compressed chat that follows its parent), and keeps those answers for 5 minutes. For a chat whose computer is offline, the page says that messages fail until it is back; the hub does not hold them (holding is only for a backend that restarts). A chat that was never bound shows as Sandbox when the plugin's fallback is the sandbox, and as on the Hermes server otherwise; the plugin's answer does not tell the hub when its fallback is `refuse`.
- **Moving a chat.** "Move to computer..." in a chat's menu, or a tap on the line under its title, binds the chat to a computer and folder of its backend; it then no longer uses the sandbox. A chat on another of the user's computers is unbound from it first, and bound back if the new bind fails. "Stop using this computer" unbinds it: as the plugin rule says, the chat then runs no commands anywhere, also not in the sandbox, until it is moved to a computer again. The hub refuses to move or unbind a chat that runs on someone else's computer, also one that follows a parent chat there, and refuses to unbind a chat whose parent chat is on a computer, because the chat would then follow the parent instead of stopping.
- **Telegram.** `/devices` lists the user's computers, `/new NAME [folder]` starts a chat on one (no folder: the last folder used there, else its first root; `~/x` is under its home, `x` under its first root), `/where` says where the attached chat runs, `/move NAME [folder]` moves it, and `/move off` unbinds it after a confirmation. `/sessions` shows where each chat runs and which ones an editor or the terminal started, and lists the user's pinned chats first, in the order set in the web page, each marked "pinned".
- **Your computers.** The gear button at the foot of the chat list opens Settings. Its Computers tab lists the user's computers with when and from where each was last used, a note when one connected from a new address (the gear then shows a dot), how its last exec leg ended (close code, reason, and whether the computer, Hermes or the hub closed it) until it connects again, Rename (`POST /api/devices/<id>/rename`) and Remove. Log out is in Settings, Account. For example, a computer whose talaria release does not match the plugin shows the plugin's `4426` reason. Every leg close is logged as `device leg closed` with `code`, `reason`, `backend_code` and `closed_by`. Remove closes the computer's connections at once on the replica that served the page, and on other replicas within `device.recheck_interval`.
- **Replicas.** Devices, pairings and wrong-code counts are in the store, so any replica serves any request. A device's legs may run on different replicas; the plugin and acp-host are the meeting point. The pairing request limit per address counts per replica. On shutdown the hub closes every device connection with 1001, and the devices reconnect, to another replica when there is one.

Set up: make a key with `openssl genpkey -algorithm ed25519 -out hub-device.pem` and give its PEM to the hub as `device.signing_key` (environment variable `HUB_DEVICE_SIGNING_KEY`) or `device.signing_key_file`. Give each Hermes pod only the public key (`openssl pkey -in hub-device.pem -pubout`); the hub also logs it in base64 at startup. Set the plugin's `backend_id` and acp-host's `acp-host.backend-id` to the hub's backend id. Give `/api/device/` a route rule with request and idle timeouts off, as for the event stream. Allow the hub to reach each backend's acp-host port (9130).

## Notices from Hermes

Hermes puts some of its own messages into a chat as user messages: the result of a background subagent (`delegate_task` in the background), the end of a background command, a message from another chat, and the summary that Hermes writes when it compacts a long chat. The page shows them as a collapsed card on the reply side, not as your bubble: a line icon, a one-line title (`Subagent finished: <task>`, `Subagent failed: <task>`, `Background command finished: <command>`, `Message from <chat>`, `Earlier messages were summarized`, or `N subagents finished` with one row per task) and under it a muted status line (Completed or Failed, the time in plain units such as `51 min`, the route or model, the number of calls; `Exit 0` for a command). Click or tap the card, or press Enter or Space, to open it: it shows the task or command and the start of the result as Markdown, with "Show full result" for the rest, and Copy puts the whole original text on the clipboard. The summary card opens to the summary as Markdown, with "Show full summary" for the rest, and shows the time and, when the summary names how many messages it replaced, `N messages before this point`. The instructions that Hermes writes for the agent (such as "You may have moved on since dispatching", or the rules and the `--- END OF CONTEXT SUMMARY` line around a summary) never show. The same cards show in the page chat of the browser extension.

The agent still gets the whole text; the cards change only what the page shows. The page reads the text itself, by its known first lines (`[ASYNC DELEGATION ...`, `[IMPORTANT: Background process ...`, `[Agent message ...`, the `[CONTEXT COMPACTION — REFERENCE ONLY] ...` header of a summary (or the older `[CONTEXT SUMMARY]:`; the text must start with it), or any text that ends with Hermes's `[INTERNAL NOTIFICATION ...]` line), so it needs nothing from the backend. A message that matches none of them stays a normal user bubble. The reader is `internal/notice` (Go, for Telegram) and `internal/web/static/notice.js`; both run against `internal/notice/testdata/cases.json`, whose texts come from the formats in Hermes. The Telegram bot sends one line instead, such as `Subagent finished: <task> (Completed, 51 min)` or `Earlier messages were summarized`. The edit and retry of a chat skips the summary when it looks for your last message.

## Agent messages

The user's agents can message each other through the hub, as Claude Code sessions do: a chat, or a subagent that a chat delegated to, lists its peers and sends one of them a message, and the target can answer the same way. It does not matter which computer each chat runs its commands on: a message goes from Hermes to the hub and back to Hermes, never through a device. The agent's tools come from the talaria device plugin (`agent_peers`, `agent_send`, `agent_set_name`, talaria docs/protocol.md section 12). The hub takes their calls from the plugin with a long poll (`GET /api/plugins/device/agents/requests`, with the hub's dashboard login), so Hermes needs no way to reach the hub.

- **Scope.** An agent reaches only the chats of its own backend and the subagents of its own delegation tree. Each person has their own backend, so one person's agents never reach another person's. A backend with devices has agent messages on when `backends[].users` names exactly one user and `groups` is empty. A backend that several people share needs `backends[].agent_messages: true`: Hermes does not record which person a chat belongs to, so all its chats then count as one person's, which they already are to the hub (every user of a backend sees and drives every chat on it). `agent_messages: false` turns it off. Only chats of the hub, an editor or the terminal count (session source `gui`, `local`, `cli`, `tui`, `acp` or `desktop`): conversations that Hermes holds itself on a messaging platform, such as a Telegram group, may have other people in them, so agents never see or reach them. The router polls a backend's plugin only when the plugin's `backend_id` is that backend's id.
- **Addressing.** `to` is a session id, a chat's short name (`agent_set_name`, unique per backend), an exact chat title, a subagent id (`sa-...`) or `parent`. A session id always wins. A name may not equal another chat's id or title, and a name of one chat that equals the title of another is refused as ambiguous, so a chat cannot take another chat's messages by its name. `agent_peers` shows each chat's id, name, title, computer and folder (or the sandbox or the Hermes server) and whether a turn runs, newest first, at most 30, without archived chats and chats older than 7 days that are not live.
- **Delivery.** A message to another chat is a new input of that chat (`prompt.submit` under the submission id `hermes-hub-agent-<id>`): an idle chat starts a turn, a busy one runs it after its current turn. A parent's message to its own running subagent is Hermes's steer, which the child reads after its current step. A subagent's message to its parent, or to a sibling, rides on the target's next tool result while the target runs; a parent chat whose turn does not run, or ends before it reads the message, gets it as a new input. A chat that runs on someone's computer runs what the message leads to with that chat's own binding and approvals, never the sender's. The hub refuses to deliver an input to a chat in yolo mode (`config.get` `yolo`), since what the message leads to would then run with no approval the user sees; a chat whose mode it cannot read is refused too.
- **Marking.** The target gets the first line `[Agent message am_<id> from <sender>]` and a paragraph that says another agent wrote it, not the user, that it is not the user's instruction or approval, and that a reply in its own chat does not reach the sender, so an answer goes through `agent_send`. The page shows such a message as a notice card "Message from ..." (see [Notices from Hermes](#notices-from-hermes)) and the sender's `agent_send` call with "Agent message to ...", so the traffic shows in both chats. The Telegram bot sends an incoming agent message to the Telegram chats attached to the target. The hub drops control and format characters (zero-width and bidi ones too), turns `@file:`-style references into a full-width `＠`, so the text cannot read files into the target's context, and turns each `[` that could open a frame marker (one that no word character or closing bracket precedes and a letter or `/` follows, such as `[OUT-OF-BAND USER MESSAGE`, `[System note:` or `[Agent message`) into a full-width `［`, so the text cannot fake the end of its frame or a note from Hermes. Devices may not submit inputs under `hermes-hub-` submission ids.
- **Approvals.** A message is text in the target's context, so it can never answer an approval: Hermes takes an approval only from `approval.respond`, which only the user's page, Telegram chat or editor sends. Approval prompts of a turn that a message started go to the user as always. A model can still follow what a message says; the frame tells it not to take the text as the user's words, but the target's approvals are the boundary. The hub checks only the chat's own yolo switch: with Hermes's `approvals.mode: off` for the whole profile, every chat runs without approvals, agent messages included.
- **Limits.** A message has at most <!-- docgen:const pkg=internal/agents name=MaxText -->`8000`<!-- /docgen:const --> characters. A chat and its subagents send at most <!-- docgen:const pkg=internal/agents name=MaxFromTree -->`20`<!-- /docgen:const --> messages, and at most <!-- docgen:const pkg=internal/agents name=MaxPair -->`8`<!-- /docgen:const --> to one target, in <!-- docgen:const pkg=internal/agents name=ShortWindow -->`10m0s`<!-- /docgen:const -->; the agents of a backend send at most <!-- docgen:const pkg=internal/agents name=MaxBackend -->`200`<!-- /docgen:const --> in <!-- docgen:const pkg=internal/agents name=LongWindow -->`1h0m0s`<!-- /docgen:const -->. `agent_peers` and `agent_set_name` are limited to 30 calls per chat tree in 10 minutes on each replica. The hub handles one send at a time per replica, so two sends cannot both pass a limit; two replicas can still each pass one. A message counts one hop more than the highest hop that any agent of the sender's tree (the chat and its live subagents) got in the last <!-- docgen:const pkg=internal/agents name=HopWindow -->`30m0s`<!-- /docgen:const -->, or than the message it answers (`reply_to`); past <!-- docgen:const pkg=internal/agents name=MaxHop -->`6`<!-- /docgen:const --> hops the hub refuses and tells the agent to stop and tell the user. The tool's description tells agents not to answer just to acknowledge.
- **Record.** The hub keeps every message (sender, target, hop, text, how it was delivered) in its store for 30 days and logs each one as `agent message` without its text.

## Deploy

- One replica: the default `store.driver: sqlite` keeps everything in the file `store.path`. Put it on a persistent volume and use the `Recreate` strategy.
- Two or more replicas: set `store.driver: postgres` and `store.dsn` (environment variable `HUB_STORE_DSN`). Connect to the database directly, not through PgBouncer in transaction mode, because the Telegram leader lock needs a session. Each replica keeps its own gateway subscriptions; a page that reconnects to another replica gets a fresh snapshot.
- To move from SQLite to PostgreSQL, set `store.import_path` to the old `store.path` for one start with the old volume mounted. The hub copies the rows once and records that in the database; later starts skip the copy, also when the file is still there.
- On `SIGTERM` the hub makes `/readyz` fail, keeps serving for `shutdown.drain_delay` (default 5s) so load balancers stop sending it requests, gives up on held messages (the chat says they were not sent), tells every event stream to reconnect, stops the Telegram bot (which frees its lock), and then waits up to `shutdown.timeout` (default 20s) for open requests. Keep the pod's termination grace period above the sum of the two.
- Give `http.public_url` the address that users open. It sets the redirect URI, the only allowed `Origin`, and `Secure` cookies (for `https`).
- The event stream is a long-lived HTTP response. Turn off the request timeout on the route (Gateway API `timeouts.request: 0s`). The hub sends a comment every 15 seconds, so idle timeouts above that are fine.
- `/healthz` answers `ok` without a login. `/readyz` answers `ok` once the hub has started, and 503 from the moment it starts to shut down; use it as the readiness probe.
