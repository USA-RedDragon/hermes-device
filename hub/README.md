# hermes-hub

[![Release](https://github.com/USA-RedDragon/hermes-hub/actions/workflows/release.yaml/badge.svg)](https://github.com/USA-RedDragon/hermes-hub/actions/workflows/release.yaml) [![go.mod version](https://img.shields.io/github/go-mod/go-version/USA-RedDragon/hermes-hub.svg)](https://github.com/USA-RedDragon/hermes-hub) [![License](https://badgen.net/github/license/USA-RedDragon/hermes-hub)](https://github.com/USA-RedDragon/hermes-hub/blob/main/LICENSE)

One web front end, behind OpenID Connect login, for many [Hermes Agent](https://github.com/NousResearch/hermes-agent) gateways. It is made for a phone first.

- One list of the sessions on every Hermes backend that you may use, live and stored.
- Open a session and continue it, also a live session that VS Code or the CLI started. The gateway keeps ownership of the session, so you can go back to VS Code at any time.
- Reasoning, tool calls (arguments, progress, result) and the reply stream live, with no refresh.
- New sessions, interrupt, approval prompts with every choice Hermes offers, and the agent's questions (pick one, pick several, or type an answer).
- Notices on the phone when Hermes needs you or is done, through Telegram and Web Push, also for chats nobody has open and for scheduled jobs (see [Notifications](#notifications)). The hub installs as an app.
- Images and files attached to a message, on the page and in Telegram (see [Attachments](#attachments)).
- Images and files the agent shows the user, such as browser screenshots, on the page and in Telegram (see [Files from the agent](#files-from-the-agent)).
- Pages: interactive HTML that the agent writes, opened full screen in a sandboxed frame, with a way to send an answer back to the chat (see [Pages](#pages)).
- Claude subscription accounts and the Claude API as models, with each account's usage and a sign-in from the hub (see [Claude](#claude)).
- Replies in Markdown, with colored code blocks and a Copy button. Model output never becomes HTML, and links open only `http`, `https` and `mailto` targets.
- A line under the chat title with the model, how full its context is (such as `41k / 131k context`, with a small meter), reply speed and the working folder. It opens to pick the model and the thinking level.
- Rename, archive and delete chats, and search their titles.
- An optional Telegram bot (`telegram.*`) that uses the same backends and permissions.
- Optional [hermes-device](https://github.com/USA-RedDragon/hermes-device) support (`device.*`): users pair their own computers, start or move chats onto a computer and folder from the web page or Telegram, and Hermes runs commands, edits files and serves VS Code there.

The hub speaks the canonical session protocol of Hermes <!-- docgen:const pkg=internal/gateway name=HermesVersion -->`v0.23.1`<!-- /docgen:const -->: JSON-RPC over the gateway's `/api/ws` WebSocket. A contract test (`internal/gateway/contract_test.go`) checks the protocol lines it depends on against a Hermes checkout (`HERMES_AGENT_SRC`, default `~/.hermes/hermes-agent`). Set `HERMES_AGENT_VERSION` to check a newer release. Before a Hermes upgrade, follow [docs/hermes-upgrade.md](docs/hermes-upgrade.md).

## How it works

Each user logs in through the OIDC provider. The hub identifies the user only by the ID token's `sub` claim, which the user cannot change, and maps it to a hub user name with `users[]`. A login whose `sub` is not in `users[]` is refused and gets no session. The `oidc.display_claim` (default `preferred_username`) is shown on screen and never used for access. A user may use a backend when their hub user name is in `backends[].users`, or a group from `oidc.groups_claim` is in `backends[].groups`. Every API call and every stream checks this. The hub stores each user's groups from the last login, so the Telegram bot can apply the same rules. Telegram links and `ui.default_backends` also use the hub user name.

```yaml
users:
  - sub: "<sub of the first user>"
    name: alice
  - sub: "<sub of the second user>"
    name: bob
```

A refused login logs its `sub` (`login refused: sub is not in users`), so you can copy the value from the hub log after a user's first try.

For each backend the hub keeps one WebSocket to the Hermes Webapp listener. It signs in with a dashboard password provider (`POST /auth/password-login`), gets a single-use ticket (`POST /api/auth/ws-ticket`) and dials `/api/ws` with the subprotocols `hermes-gateway-v1` and `hermes-gateway-ticket.<ticket>`. Viewers of the same session share one gateway subscription.

The browser gets each session as server-sent events. Each event has the hub's sequence as its id. When the browser reconnects, it sends the last id back (`Last-Event-ID`) and gets only the events that it missed. If the hub no longer has them, the browser gets a new snapshot. When the connection to a gateway drops, the hub dials again, replays the missed frames with `session.events.since` and attaches again with `session.resume`.

When a Hermes backend restarts, the hub holds the messages that users send to it. A message is held when `prompt.submit` cannot reach the backend: the gateway answers HTTP 503 `gateway_not_ready`, closes the socket with 1013, refuses with `runtime_draining`, or cannot be dialed. The hub answers `202` with `{"status":"held"}`, tells the chat "Hermes is restarting. Your message will send when it is back.", and sends the held messages of each chat in order when the backend is back. It sends each one under the `submission_id` of the first try. Hermes keys an admission by principal, session and `submission_id`, so a retry after a lost answer never runs a message twice. A message that waits longer than `hold.timeout` (default 10 minutes) is dropped, and the chat says that it was not sent. Held messages are kept in the memory of the replica that took them; the hub sends their events to the other replicas through PostgreSQL `NOTIFY`, so a page whose stream runs on another replica also sees them. Events sent while a replica's listener reconnects are lost to that replica. If the connection drops after a message went out, Hermes may have it although the hub got no answer; when the hub then gives up on it, the chat says so.

When the hub attaches to a session, it sets the session's `show_reasoning` control on (`config.set`), so that sessions that VS Code started through ACP also stream reasoning. The gateway reads this flag when a turn starts, so the change shows from the next turn. Set `backends[].show_reasoning: false` to turn this off.

## The page

Every user gets the same page. It opens one chat with the user's default backend (`ui.default_backends`, as `user=backend`, else their first backend), with live activity in plain words. "New chat" starts a fresh session there. "More" opens all backends and sessions, and each tool step keeps its details behind "details". Users differ only in which backends they may use.

When a reply is done, its tool steps fold into one line ("Read a file, ran a command (3.4s)") that opens to show them. File edits show their diff and commands show their output.

The context readout comes from the `usage` object that Hermes sends in `session.usage` during a turn, in `message.complete` and in the session's snapshot: `context_used` (the tokens of the last request) of `context_max` (the model's window). Before the first reply after a restart, only the window (`context_length` in the snapshot info) is known, so the line shows only that. The meter turns the warning color at 80 percent. When Hermes summarizes older messages to make room (a `status.update` of kind `compacted`, or a higher `compressions` count in the usage), the chat gets the note "Older messages were summarized to make room." After a model switch the line drops the old window, and shows the new one after the next reply, since Hermes builds the new model's agent only then. A leading `~` means Hermes estimated the count.

Chat changes use the gateway's `session.mutate` (rename, archive, delete, model), fenced on the session's revision. The model list comes from `model.options` and shows only models of providers that Hermes is signed in to. The thinking level is `config.set` with the key `reasoning`; Hermes applies it from the next turn. A chat that is working or has messages waiting cannot be deleted.

Syntax colors come from [highlight.js](https://highlightjs.org/) 11.11.1 (BSD-3-Clause), in `internal/web/static/vendor`.

## Activity

"Activity" in a chat's top bar opens a sidebar with the work the chat runs beside its turns, with the number that runs now. It has two tabs, each with a Now and a Finished part. A row opens to show a live tail. On a phone the sidebar slides over the chat, and the button shows only an icon and the count. A `delegate_task` step or a background `terminal` step in the chat opens the sidebar on its rows. The chat list shows the same count next to each chat (`subagent.roster`).

- **Subagents** are the children that `delegate_task` starts. The page builds each row from the session's `subagent.spawn_requested`, `subagent.start`, `subagent.thinking`, `subagent.tool`, `subagent.progress` and `subagent.complete` events, and from `GET /api/sessions/<backend>/<session>/activity`, which reads `subagent.list`, `process.list` and `delegation.status`, every 3 seconds while the sidebar is open or anything runs and every 20 seconds otherwise. A child shows under the subagent that started it. An open row of a running subagent shows the end of its live transcript (`subagent.tail`). "Message this subagent" queues text that the subagent reads at its next step (`subagent.steer`), and Stop interrupts it (`subagent.interrupt`). Pause and Resume set Hermes's switch for new subagents (`delegation.pause`): it covers every chat of the backend, and subagents that run go on. Hermes does not say which subagent asks for an approval, so the hub shows an approval in a subagent's row only when the command matches that subagent's last tool call or only one subagent runs; the chat shows it in every case.
- **Background** has the chat's background commands (`terminal` with `background`) and its `/bg` prompts. Stop kills one command (`process.kill`). "Full output" shows what Hermes keeps of a command's output, the last 32,768 characters: Hermes v0.23.1 names no output file for a background command, so there is no file to open. There is no "Run again": Hermes has no method that starts a command again. `/bg <prompt>` (or `/background`) in the message box starts a background prompt (`prompt.background`): a separate agent runs it with the chat's settings, and its answer shows in the row when it is done (`background.complete`). Its tokens come from Hermes's records through the device plugin's usage route. The hub refuses `/bg` in a chat on a computer, and in one taken off its computer: Hermes runs the prompt as a session of its own, so its commands would run where new chats run (the sandbox or the Hermes server) and not on the computer. Hermes stores a background prompt as a chat of its own (`bg_...`). Its row has no link to the chat that started it, so the hub knows it by the `bg_` ID prefix. The hub keeps such chats out of the chat list, the search and Telegram topics, since they belong to the chat that started them. "Open chat" on a finished prompt's row opens its full transcript.

Every call names the chat, and the hub checks that the user may use its backend. The gateway's own handlers (`gateway/session_ancillary.py`) act only on the children and processes of the named chat, and the hub also checks that the subagent or process is in that chat's own list before it sends `subagent.steer`, `subagent.interrupt`, `subagent.tail` or `process.kill`. `delegation.status` also lists the subagents of every chat of the gateway; the hub passes on only whether new subagents are paused.

**Tokens.** The top bar shows the tokens of the turn that runs (or the last one), in and out, and under that the chat's totals in and out, the share of input that came from the cache and the reply speed, from the session's `session.usage` and `message.complete` usage. In counts every token sent to the model, cached or not (`prompt_tokens`). Hermes counts a turn's output itself (`last_turn_tokens`); the hub works out its input from the counters at the turn's start and adds both to the events as `hub_turn`. When the hub cannot tell where the turn started, for example when Hermes rebuilt its agent and the counters do not match, it shows only the output. On a phone the line shows the in and out counts, the chat's totals and the speed. The sidebar shows the tokens of each subagent (from `subagent.complete`) and background prompt, and the totals of the tab; background commands use no tokens. Subagents and background prompts are not part of the chat's own counts.

## Attachments

The paperclip by the message box attaches files; pasting or dropping files onto the chat does too. Each file shows as a chip, with a thumbnail for an image, until it is sent or removed. The sent message shows them. A chat opened again later shows the images again through the hub's file route (see [Files from the agent](#files-from-the-agent)), and other files by name.

- **Images** (PNG, JPEG, GIF and WebP, found by their first bytes) go to the model. The hub stages each one with `image.attach_bytes`, which the gateway saves in the profile's `cache/images`, and names them in the `attachments` of the `prompt.submit`. Hermes takes up to 10 images of up to 25 MB each. Hermes decides whether the model reads them itself or an image model describes them. When the session's tools have no `vision_analyze`, Hermes most likely has neither, and the hub tells the user that the model may not be able to see the images. For a chat on a computer or the sandbox, the hub also writes each image to the chat's folder there, as it does other files, so the agent's tools can open it.
- **Other files** go where the session's tools can read them. For a chat that runs on a computer or the sandbox, the hub sends the file to the device plugin, which writes it into `.hermes/attachments` of the chat's folder on that device (hermes-device docs/protocol.md section 9). For a chat that runs on the Hermes server, the hub hands it to Hermes with `file.attach`. The message then gets a line that names the file and its path. A file is at most 32 MB. The plugin takes 2 uploads at a time and the hub stages 4 messages with attachments at a time; more get a note to try again.
- One message takes at most 10 files, 64 MB in all. A message with files cannot be a slash command. Hermes must be up to take the files, so while it restarts the hub refuses such a message with a note instead of holding it; it holds one only when Hermes took the files and then went away before the message itself.
- **PDFs** (files that start with `%PDF-`, or named `.pdf` with `%PDF-` in their first 1024 bytes) go where the session's tools can read them, as other files do, and the hub also reads them itself, since Hermes' `pdf.attach` is not served on the gateway's socket. The hub runs `pdftotext -layout` for the text and `pdftoppm` for page images, <!-- docgen:const pkg=internal/pdf name=ImageSide -->`1280`<!-- /docgen:const --> pixels on the long side (about 120 dpi for a Letter or A4 page). The message gets a line that says how many pages the PDF has and which ones are shown, then the text between `<untrusted-pdf-text>` markers with a random id, marked as data from the file and not from the user. One message carries at most <!-- docgen:const pkg=internal/service name=maxPDFText -->`60000`<!-- /docgen:const --> characters of PDF text, shared by its PDFs, and the hub reads text from at most <!-- docgen:const pkg=internal/pdf name=MaxPages -->`2000`<!-- /docgen:const --> pages of each; the agent reads the saved file for the rest. The first pages go to the model as PNG images in the slots of the 10 images that the user's own images leave free. The page shows a PDF with its page count; under "pages" on its chip the user can pick the pages to show, such as `3-10`, and the hub then reads the text of those pages only. Text in the PDF that looks like these markers or like the hub's notes is changed so it cannot pass for them. An encrypted or damaged PDF, or one whose text takes too long or too much memory to read, goes as a plain file, and the user gets a note that says why. When rendering a page takes too long, the agent gets the text and the pages rendered before it.
- The hub runs the PDF programs (poppler-utils, in the container image) with a clean environment, in a new directory under `TMPDIR` that it deletes afterwards, with a 60 second timeout for each PDF and limits of 192 MB of address space and 60 CPU seconds for each program. It reads one PDF at a time, so the programs fit in a 512 MiB pod next to the hub. The PDFs of one message get at most 2 minutes, and at most half of the time the caller has left (a Telegram message has 30 seconds). At startup the hub removes work directories older than 10 minutes that a stopped hub left behind. Without poppler-utils on `PATH` the hub logs a warning at startup and PDFs are plain files.

## Files from the agent

The agent shows a file to the user with a `MEDIA:<path>` line in its reply, as for Hermes' own messaging platforms (`gateway/platforms/base.py` `extract_media`). The file can be on the Hermes server or on the computer or sandbox that runs the chat. hermes-device's `browser_screenshot` tool saves a screenshot of a browser tab and tells the model to put such a line in its reply. The page hides the line and shows the file in its place: an image inline, which opens full size, a card that opens an HTML file as a [page](#pages), or a chip that downloads any other file. A `browser_screenshot` tool card shows the screenshot too. Telegram gets the reply text without the line, then each image as a photo (a file when Telegram refuses the photo, or when it is over 10 MB) and each other file as a document, up to 50 MB, except an HTML file, which gets a link to its page. The bot sends at most 10 files of one reply. Lines in code blocks, inline code examples and quotes stay as text.

The page asks `GET /api/sessions/<backend>/<session>/media?path=<path>`, and the hub serves the file only when all of these hold:

- the user may use the backend;
- a reply of that chat names the path with a `MEDIA:` line, a `browser_screenshot` result of that chat names it, or a message of that chat names it as an attached image (`[Image attached at: <path>]` or `@image:<path>`);
- the path is absolute and clean, with an extension Hermes delivers.

The hub then reads the file from one of two places:

- **The Hermes server**, when the path is under one of the backend's `media_roots`, or, when it has none, is an image in a `browser_screenshot` folder (`<dir>/cache/screenshots/hermes-device/<session>/<file>`) or among attached images (`<dir>/cache/images/<file>`). `<dir>` can be any folder, so on a host with more than one Hermes home, set `media_roots` to this backend's folders, such as `<HERMES_HOME>/cache`. The hub reads it through the Hermes web server, the way the Hermes Webapp page downloads a file: `POST /api/files/ticket` mints a ticket bound to the path, and `GET /api/fs/download` with that ticket streams the file.
- **The computer or sandbox that runs the chat**, for any other path, and for a path under the media roots that the server does not have. The hub asks the hermes-device plugin (`GET /api/plugins/device/sessions/<session>/files?path=<path>`, hermes-device docs/protocol.md section 9), which reads the file over the device's exec leg from the device that serves that chat only. The plugin applies the read rules of file tools there: the path and its real path must be inside the device's roots and not a credential path, the last part must not be a symbolic link, and the file must be a regular file with one hard link, at most 32 MiB. A chat that runs on the Hermes server gets no device files. At most 2 such reads of one backend run at once; the others wait. Browsers may not cache device files (`Cache-Control: no-store`); server files keep `private, max-age=300`. A Telegram chat gets each file the reply names, so in a group every member gets the device file too.

An image (PNG, JPEG, GIF or WebP by both its extension and its first bytes) comes back inline as that type; anything else comes back as `application/octet-stream` with `Content-Disposition: attachment`. Every answer has `Content-Security-Policy: default-src 'none'; sandbox`. A file is at most 64 MB from the server. When the computer is offline, the page gets `503` and Telegram a note that says so. Device files need a hermes-device plugin with the read route; with an older plugin they are not shown.

## Pages

A page is an interactive HTML document that the agent makes for the user, such as a list of entries with checkboxes, a mockup or a report. The agent writes the page in its reply as a fenced block whose info string is `page`:

````
Here are the candidates.

```page
<!doctype html>
<title>Pick entries</title>
...
```
````

The block also opens with `html page` or `hermes-page`, and closes with a fence of the same character that is at least as long. A block inside another fenced block, in a quote, or not closed stays as text. A reply can have more than one page. The page block works wherever the chat runs (the Hermes server, a sandbox or a computer), because the page travels in the reply. An HTML file (`.html` or `.htm`) that a reply names with `MEDIA:<path>` is also a page, under the rules of [Files from the agent](#files-from-the-agent), on the Hermes server or on the chat's computer or sandbox.

The page shows a card with the page's `<title>` and an Open button in place of the block. Open shows the page over the chat with Back, Reload and Download. Its address is `#/page/<backend>/<session>/<ref>`, where `<ref>` is the page's id (the first 32 hex digits of the SHA-256 of the block's text) or the file's path. The browser computes the id with Web Crypto, so the hub must be served over HTTPS or from localhost. Back returns to the chat and keeps the page's state until another page or chat opens. Telegram gets a link to that address for each page, since Telegram cannot run one.

The frame loads `GET /api/sessions/<backend>/<session>/page?id=<id>` (or `?path=<path>`). The hub serves the page only to a user who may use the backend, only when a reply of that chat has the block (or names the file), and only to a frame: a request whose `Sec-Fetch-Dest` is not `iframe` is redirected to the page's address. `GET .../page-info?path=<path>` answers the title of a file page.

Pages are isolated from the hub and from each other:

- The frame has `sandbox="allow-scripts allow-forms allow-modals allow-popups"` without `allow-same-origin`, and the answer has the same flags in a `sandbox` CSP directive, so the page runs in a new opaque origin even if it is loaded some other way. An opaque origin has no storage: `localStorage`, `sessionStorage`, IndexedDB and `document.cookie` throw, so nothing is kept between loads, nothing is shared between pages, and the page cannot reach the hub's storage or cookies. It cannot read the hub's document (`parent.document` throws) or navigate the hub's window.
- The CSP allows inline script and style, scripts from `https://cdnjs.cloudflare.com/ajax/libs/`, `https://cdn.jsdelivr.net/npm/` and `https://unpkg.com/`, styles from `https://fonts.googleapis.com` and fonts from `https://fonts.gstatic.com`, and images and media from `data:` and `blob:` URLs. It blocks everything else: `fetch`, XHR, WebSocket and EventSource (`connect-src 'none'`), images and frames from any host, form submission, workers and `<base>`. Only the hub's origin may frame the page. The answer also has `Referrer-Policy: no-referrer`, `X-DNS-Prefetch-Control: off` and `Cache-Control: no-store`.
- A request from the page itself to the hub carries no session cookie (the cookie is `SameSite=Lax` and the page's origin is another site), and the API refuses it as cross-site.

The CSP cannot stop a page from navigating its own frame or opening a window to another site, and the browser does not apply it to WebRTC. So a page can send what it shows, and what the user types into it, to a site in a URL. The agent writes the page and can already reach the internet from its tools, so this gives the agent no new access to data, but do not type secrets into a page.

The hub puts a small script at the start of every page that defines `window.hermes`:

- `hermes.send(text)` puts text in the chat's message box, after any text already there, closes the page and shows the chat. The user reviews the text and sends it. A click on an element with a `data-hermes-send="<text>"` attribute does the same.
- `hermes.copy(text)` copies text. It tries the frame's own copy command, then the hub's clipboard access, and else shows the text selected in a dialog for the user to copy.

The script talks to the hub only over a `MessagePort` that the hub's frame sends to the page on its first load. The hub ignores `postMessage` to its window, so another frame or window cannot speak for the page. When the frame loads a second document (the page followed a link, for example), the hub closes the port and says that the page left; Reload starts it again. A page that leaves before its first load ends is not noticed, and the document it went to gets the port; that document came from the page, so it can do nothing the page could not. While the page is hidden behind the chat, the hub ignores what it sends, and it drops a message of more than 200000 characters.

## Memory

"Memory" in the sidebar opens a page with three tabs for each backend the user may use. A count by it shows memory writes that Hermes waits to have approved. Running chats keep the memory they loaded at their start, so changes apply to new chats.

- **Notes** and **About you** are Hermes's built-in memory, `MEMORY.md` (Hermes's own notes) and `USER.md` (its profile of the user). Each shows its entries with Edit and Delete, a meter of the characters used against the limit from Hermes's config (`memory.memory_char_limit`, default 2,200, and `memory.user_char_limit`, default 1,375), and, when `memory.write_approval` is on, the writes Hermes staged with Approve and Reject. Under "Advanced" are the file path, a switch for `memory.write_approval` and an editor for the whole file. The hub reads and changes them through the hermes-device plugin's memory routes (hermes-device docs/protocol.md section 9.1), which use Hermes's own memory store, so its limits, file lock, threat scan and approval rules hold. The switch uses the dashboard's `PUT /api/config`. A backend whose Hermes has no hermes-device plugin with those routes has no Notes tabs.
- **Learned** lists the facts ("conclusions") Honcho drew from the user's chats, for a backend with `backends[].honcho`. It searches by meaning, sorts newest or oldest first, filters Hermes's view of the user (observer `ai_peer`) or the user's own words (observer `user_peer`), and deletes one or several facts after a confirmation. A fact links to the chat it came from when its Honcho session id is a chat of that backend. Under "Advanced" are the counts, the profile card (Hermes's card of the user, else the user's own), a form that adds a fact as Hermes's view, and an export of every stored copy as JSON. Before it deletes a fact, the hub reads it and checks that it is about `user_peer`. The Honcho API key stays in the hub: browsers never get it.
- Honcho often stores one fact twice, once in each view. The Learned tab shows such a fact once, marked "Both views", and Delete removes every copy. Two copies are one fact when their text is the same after case and runs of white space are ignored; text that differs in any other way, such as punctuation, shows as two facts, so a delete never removes text the user did not see. A paired fact matches both view filters. The counts are of distinct facts, and Advanced also says how many copies Honcho stores. To pair copies and count facts, the hub reads every stored copy for each list and count, at most the newest 10,000. Past that limit, a copy older than the newest 10,000 is not paired, so a delete can leave it behind.
- Honcho marks the kind of each conclusion in its `level` field. Its deriver writes `explicit` facts, taken straight from one message ("From one message"). Its dreams later write `deductive` ("Deduced"), `inductive` ("Pattern") and `contradiction` ("Conflict") conclusions from facts it already has. The Learned tab shows only the dream conclusions at first; "Show all" brings back the facts from single messages. A paired fact shows as condensed when any copy is. A fact added on the page is `explicit`, so after a save the tab turns on "Show all".

The hub checks on every request that the user may use the backend, so a user sees only the memory of the backends they may use. A backend has one `MEMORY.md`, one `USER.md` and one Honcho user, so every user of a shared backend sees and changes the same memory. Give each person their own backend, with `honcho` set to that person's own workspace and a key scoped to it.

The whole-file editor sends the entries it showed with the edited text. Entries Hermes added meanwhile stay; when Hermes changed or removed one of the shown entries meanwhile, the save fails and asks for a reload. The Learned tab shows only conclusions whose observer is `ai_peer` or `user_peer`, so conclusions of other peers in the workspace never show and cannot be deleted from the hub. A fact links to its chat only when Hermes names its Honcho sessions after its own session ids (Honcho `sessionStrategy: per-session` without a peer prefix); with other strategies the link does not show. Honcho errors go to the hub log; users get a short message.

## Search

The search box over the chat list matches chat titles as the user types. From the second character it also searches the messages of every chat on each backend the user may use, and lists the chats with matching messages under "In messages": the title, the date the chat was last used and up to two short excerpts with the matches marked. A click opens the chat at the first matching message, or says that the message is further back than the chat shows.

The hub asks each backend's hermes-device plugin (`GET /api/plugins/device/search?q=<text>`, hermes-device docs/protocol.md section 9.2), which runs Hermes's own full-text search (`SessionDB.search_messages`, FTS5 with Hermes's fallbacks) over user and assistant messages, without the background sources that Hermes's `session_search` tool hides. A match in an earlier part of a chat that Hermes compressed opens the chat that continues it. The search takes Hermes's syntax: words, `"phrases"`, `AND`, `OR`, `NOT` and `prefix*`. Hermes's gateway has no search call, so the search needs a hermes-device plugin with that route; a backend without one shows a note under the results. The excerpts are text: the page never renders them as HTML.

## Usage

"Usage" at the foot of the chat list opens a page for one backend and the last 7, 30 or 90 days:

- **Tokens by day**, **Chats** and **Models**: the token counters Hermes keeps for each session and each model in its session store, read through the plugin (`GET /api/plugins/device/usage`). Hermes keeps one total per session, not one per call, so a chat counts on the day it was last used. Context is how full a chat's context was in the latest usage event the hub saw for it.
- **API limits**: the rate limits each provider last reported, from the `rate_limit` of the `session.usage` events the hub sees while chats run. Hermes parses only `x-ratelimit-*` headers (`agent/rate_limit_tracker.py`); it does not read Anthropic's own `anthropic-ratelimit-*` headers or any spending limit of an API key, so for Anthropic the section stays empty until Hermes does. Ollama has no API limits; the section shows the tokens per second and seconds per call that Hermes measured in the latest chat of each model. Each hub replica keeps what it saw in memory, since it started.
- **Local GPU**: with `usage.prometheus_url` set to a Prometheus query API that scrapes [ollama-priority-proxy](https://github.com/USA-RedDragon/ollama-priority-proxy)'s metrics, the time in the last 24 hours, 7 days and 30 days that Ollama had a request running (`ollama_priority_proxy_in_flight` above 0, checked each minute), the summed request time of people's and of background requests (`ollama_priority_proxy_upstream_duration_seconds`), and the number of requests. Hermes itself records no request times.
- **Memory backlog**: Honcho's queue for the backend's workspace (`GET /v3/workspaces/<workspace>/queue/status`), for a backend with `backends[].honcho`.

## Claude

A backend's Hermes can offer Claude models two ways. Each chat picks one in the model list, like any other model:

- **Subscription accounts.** The claude-accounts Hermes plugin adds one model provider per Claude account, named `claude-<slot>` (such as `claude-account1`). It runs the official `claude` CLI with that account's config folder. The model list shows Hermes's name for each provider, such as "Claude (account1)".
- **API key.** Hermes's built-in provider `anthropic`. The hub shows it as "Claude API" in the model list and on the line under the chat title. Hermes does not record Anthropic's `anthropic-ratelimit-*` headers, and no Anthropic API tells an API key how much of a plan's monthly API credit is spent, so the hub shows only the name. If Hermes reports limits for `anthropic` some day, the API limits on the Usage page show them.

The hub calls the plugin's routes on the Hermes web server with its dashboard login, as for the device plugin: `GET /api/plugins/claude-accounts/accounts`, and for one account `GET .../accounts/{id}/usage`, `GET .../accounts/{id}/status`, `POST`, `GET` and `DELETE .../accounts/{id}/signin` and `POST .../accounts/{id}/signin/code`. A backend whose Hermes answers 404 has no plugin, and the hub shows none of this for it.

**Line under the chat title.** For a chat whose provider is one of the plugin's accounts (the hub looks the provider up in the account list), the line shows the account's name, the share of the 5-hour session and of the week that it used, and when each resets, in `claude.time_zone` (default America/Chicago): for example "5h 12% (resets 3:40 PM CST)". The page reads the accounts at most once a minute, and the chat's account again after each reply. The hub keeps what it read for a minute, or 15 seconds when a reply asks again. An account that is not signed in shows "not signed in", with a note under the title.

**Usage page.** "Claude accounts" lists each account: its name, the email it is signed in to (or was last signed in to), its plan, whether it is signed in, and each usage window with the share used and the reset time. Claude admins also get Sign in, or Sign in again.

**Sign-in.** The plugin runs `claude auth login` for the account. Sign in starts it (`POST .../signin`; a sign-in that already runs is reused) and opens a dialog. The dialog first names the account: its name, the email it was last signed in as when known, and why it needs a sign-in (its first sign-in, or the login expired or was revoked). Then it shows the link to the Claude sign-in page and a box for the code that page shows. The hub passes the code to the plugin (`POST .../signin/code`) and shows the result: the email the account signed in to, or why it failed. Cancel sign-in stops it (`DELETE .../signin`). The plugin stops the CLI 10 minutes after it started.

**Lost login.** When a turn on a Claude account ends with the plugin's error "Claude Code is installed but has no usable login", or with an upstream 401 (`status 401` or `authentication_failed`), the hub asks the plugin for the account's status. When the account is signed out:

- The chat gets a note that names the account, the email it was last signed in as and why, with Sign in for Claude admins.
- Each Claude admin of the backend gets a "Claude sign-ins" notice on Telegram and Web Push (see [Notifications](#notifications)), at most one per account in 30 minutes. The Web Push notice names the account in the same words and says to open the hub to sign in, with the chat's link; it never carries the sign-in link.
- On Telegram the hub starts the sign-in as that admin (as Sign in on the page does) and sends the admin the sign-in link, in the General topic of their linked group or else in their private chat, such as "Claude (account1), last signed in as alice@example.com". The message asks for a reply (Telegram opens the reply box): sign in on the linked page, then reply to the message with the code. Only the admin the message went to may answer; the bot passes the code to the same sign-in as the page's dialog, deletes the message with the code when it may (in a group the bot needs the right to delete messages), and edits the sign-in message to show the result: "Signed in as" the email, "Sign-in failed" and why, or "Expired" when the sign-in ended first. A code that Claude refuses can be sent again. When the hub cannot start the sign-in, Telegram gets the plain notice instead.

**Security.**

- `claude.admins` lists who may sign the accounts of each backend in, as `user=backend` pairs (environment variable `HUB_CLAUDE_ADMINS`, such as `alice=main`). Empty, the default, is nobody. Only these users see the sign-in controls, and the hub refuses (403) every other user who tries to start, read, answer or cancel a sign-in. The other users of the backend see usage only.
- The sign-in routes need the session's CSRF token and a same-origin request, like the rest of the API.
- The sign-in link goes only in the answer to the admin who asked for it, and on Telegram only to that admin's own chat or group. The account list leaves it out, and chat notes and Web Push notices never carry it.
- The hub passes the code straight to the plugin. It never logs, stores or sends back the code, and it does not log the link. The page clears the code box when it sends the code, and the Telegram bot deletes the code's message.

## Chat files

For a chat that runs on one of the user's own computers or in the sandbox, "Files" in the chat's header opens a read-only view of the chat's folder:

- **Folder** lists the chat's folder and lets the user go into its folders and up to the computer's root. It shows a text file with syntax colors (up to 1 MB), an image, and offers any file, such as a PDF, as a download. The browser reads every file as a download (`application/octet-stream`, `Content-Disposition: attachment`, `Content-Security-Policy: default-src 'none'; sandbox`) and never as a page.
- **Changes** lists the files the agent wrote in the chat with `write_file` and `patch`, from the tool calls Hermes stored, and, when the folder is in a git repository, what git shows as changed in the folder since the last commit, with its diff.

The hub asks the device plugin (`GET /api/plugins/device/sessions/<session>/tree`, `/files`, `/diff` and `/changes`, hermes-device docs/protocol.md sections 9 and 9.2). The plugin applies the read rules of file tools to every folder, file and changed path: inside the device's roots and not a credential path, for the path and its real path on the device. It leaves protected entries out of listings and diffs, runs git read-only, and limits a diff to 1 MiB and to the chat's folder. The hub shows the view only for a chat on the user's own computer or the sandbox; a chat on another person's computer or on the Hermes server has none.

## Set up a Hermes backend

The hub needs the Hermes Webapp listener on an address that it can reach, with a password sign-in. On a non-loopback bind, Hermes always requires sign-in. Add this to the backend's Hermes `config.yaml` (the device's `~/.hermes/config.yaml`, or the cluster instance's config) and restart its gateway:

```yaml
webapp:
  enabled: true
  host: 0.0.0.0
  port: 9120
dashboard:
  basic_auth:
    username: hub
    password_hash: "scrypt$..."
    secret: "<32 or more random bytes>"
```

- Make `password_hash` with `plugins.dashboard_auth.basic.hash_password('<password>')` in the Hermes Python environment. The environment variables `HERMES_DASHBOARD_BASIC_AUTH_USERNAME`, `_PASSWORD_HASH`, `_PASSWORD` and `_SECRET` override these keys.
- Set `secret`. Without it, Hermes makes a random key at each start, so each restart signs the hub out (the hub signs in again by itself).
- Open TCP port 9120 only to the hub (on a device: a host firewall rule for the cluster's node addresses or the tailnet; in the cluster: a network policy).
- Put the same user name and password in the hub's `backends[]` entry, with `provider: basic` (the default).

### Context size

Set the context window of a local model in the backend's Hermes `config.yaml`, once for that model:

```yaml
model:
  context_length: 131072
  ollama_num_ctx: 131072
```

- `model.context_length` is the window that Hermes plans for: the readout's total and the point where Hermes summarizes older messages. It also caps the window that Hermes reads from Ollama.
- `model.ollama_num_ctx` is the `num_ctx` that Hermes sends to Ollama with each request. Without it, Hermes asks Ollama for the model's largest window, capped by `model.context_length`.
- Set both to the same value, sized for the GPU's memory. Hermes reads them when it builds a chat's agent. Restart the gateway after a change so that every chat picks it up.

The size is not a per-chat setting on purpose. Ollama loads a model again when a request asks for a different `num_ctx`, so two chats with different sizes on the shared GPU would make Ollama reload the model each time they take turns. The hub has no per-chat choice for API models either: Hermes v0.23.1 has no session-scoped context or compression setting on the gateway. `session.mutate` with operation `model` takes only `model`, `provider`, `confirm` and `reasoning`, and `config.set` takes no `model.context_length` or `compression.*` key.

When a chat switches to another model, Hermes drops `model.context_length` from that chat's settings and takes the new model's window from its model data. To pin the window of another local model, give it a `context_length` under its name in the `models` of its `custom_providers` entry.

## Set up Authentik

1. Create an OAuth2/OpenID provider: client type confidential, redirect URI `https://<public host>/auth/callback` (strict), signing key set, scopes `openid`, `profile` and `email`. Authentik's default `profile` scope mapping sends `preferred_username` and `groups`.
2. Create an application with slug `hermes-hub` that uses the provider. The issuer is then `https://<authentik host>/application/o/hermes-hub/`.
3. Bind the users or groups that may log in to the application.
4. Keep the provider's subject mode at "Based on the User's hashed ID" (the default). Put each user's `sub` in the hub's `users[]`; the values belong in the deployment config, not in this repository.
5. Give the hub `oidc.issuer_url`, `oidc.client_id` and `oidc.client_secret`.

## Telegram

Set `telegram.enabled`, `telegram.token` and `http.public_url`. A Telegram user sends `/link` to the bot and gets a link to `/link/telegram?token=...`. That page needs a hub login and asks the user to confirm; only the confirmation (a POST with the CSRF token) links the account. A link token is valid for <!-- docgen:const pkg=internal/store name=LinkTokenTTL -->`10m0s`<!-- /docgen:const --> and works once.

`/status` shows the attached chat's model and how full its context is, such as `Context: 41k / 131k (31%)`, from the same usage figures as the page.

Each turn gets one status line: a single message that the bot edits in place, at most once every `telegram.edit_interval`. While Hermes works it is one line: what runs now ("Thinking…", or "Running terminal `go test ./...`"), the number of steps so far, the time and the turn's tokens, such as "Running terminal `go test ./...` · 5 steps · 1m 12s · 14k in, 1k out". Telegram folds an expandable quote again each time its message is edited, so the running line has no quote. Its Steps button sends a new message with the steps and the end of the model's thinking so far in a quote; the bot never edits that message, so a quote opened there stays open. When the turn ends the bot edits the status line one last time, and then never again: it says what the turn did, such as "Worked for 2m 5s: ran 3 commands, edited 1 file · 31k in, 3k out", with all the steps and the end of the thinking in a quote, and the Steps button goes away. The token counts are the turn's, as on the page (see [Activity](#activity)); they show from the turn's first usage event, and only the output count shows when the hub cannot tell the input. With `telegram.steps: collapsed` (the default) the quotes are folded and open on a tap; `expanded` shows them open; `off` leaves out the quote and the Steps button. The reply is always a message of its own.

**Approvals and questions.** An approval ("Needs you") shows the command and has a button for each choice that Hermes offers: Once, This chat, Always and Deny. A question has a button for each of its choices (up to 10; more get numbered buttons), Other answer and Skip, and a question with several picks toggles its choices and has Send. To give an answer of your own, reply to the question's message (Telegram's Reply), or press Other answer, which asks for a reply. A question without choices asks for a reply at once (Telegram opens the reply box); a reply of `/skip` skips it. A message that is not a reply to a question goes to the chat as usual. When a prompt is answered, the bot edits its message: it shows what became of it ("Approved once", "Answered: main", "Skipped") and who answered, and the buttons go away. A prompt that is answered somewhere else, such as on the page, shows "Answered elsewhere"; one that Hermes cancels shows "Cancelled"; one whose time runs out (Hermes's `timeout_s`) shows "Expired". The buttons of an old message then answer "This request is no longer pending."

A photo, an image or other file, a video or a voice note sent to the bot goes to the chat like an attachment on the page, with its caption as the message. A PDF gets its text and first pages read as on the page; the bot cannot pick its pages. The photos and files of one album go as one message. Telegram lets bots download files of up to 20 MB, so the bot answers a larger one with a note instead.

Telegram lets only one process long-poll a bot token. With `store.driver: postgres`, the replicas elect one leader with a PostgreSQL session advisory lock, held on a connection of its own. Only the leader polls. The other replicas try to take the lock every `telegram.leader_retry` (default 2s), so one of them takes over a few seconds after the leader stops. If the leader dies without closing its connection, PostgreSQL frees the lock when its TCP keepalive gives up, after about 15 seconds. The leader checks its lock every 2 seconds and stops polling when the check fails. With SQLite there is one replica, and it always leads.

The bot streams each chat's session through a subscription in the leader's own process. Hermes sends every session event to every subscriber, so a turn that a page started on another replica still reaches the chat. The store keeps each chat's session and the bot's update offset, so a new leader attaches every chat again and carries on from the last update the old leader finished. A leader that loses its lock stops after the update it is handling. The bot sends each message under a submission ID derived from its Telegram update, so if a new leader handles an update again, Hermes still runs the message once. If a turn runs while the leader changes, the new leader can repeat that turn's progress messages in the chat.

A chat can ask Hermes to schedule a task (Hermes cron, `cronjob_manage`). Hermes writes each result into the chat it was scheduled from as a note, not as a turn. The page shows the note as a result card, and the bot sends it to every Telegram chat attached to that session. A chat started on the page sends its results only to the page until a Telegram chat attaches to it.

### A topic for each chat

Without more setup, each person talks to the bot in one private chat, which follows one hub chat at a time. A person can instead link a private group with Topics to the bot. Then each of their hub chats gets its own topic in that group, so replies of different chats never mix. Each hub user links their own group; the private chat with the bot keeps working for anyone without one.

To set it up:

1. Link your Telegram account first: send any message to the bot in a private chat and follow the link.
2. In Telegram, make a new group. Add the bot to it.
3. Open the group's settings and turn on Topics. (This turns the group into a supergroup. Do this before step 5: the group's ID changes.)
4. Make the bot an admin of the group, with the rights to manage topics and to delete messages (it deletes the topics of deleted chats).
5. In the group, send `/link`. The bot checks that Topics are on and that it may manage topics, and links the group to the hub user of the Telegram account that sent `/link`. Only a linked Telegram account can link a group, and only to its own hub user. Linking a new group replaces the person's earlier group.

How it works:

- **Topics.** Every `telegram.topic_sync` (default 20s) the bot lists the person's chats. A chat that started after the link, or one that runs, gets a topic named after the chat's title, plus where it runs when that is a computer or the sandbox, or "scheduled" for a scheduled job's chat, such as "Fix CI · laptop". When the title changes, the topic's name follows. Archived chats get no topic, and neither do the conversations that Hermes holds itself on a messaging platform (they may have other people in them), its subagents or its `/bg` prompts (`bg_...` sessions). The store keeps each group and its topics, so a new leader carries on.
- **Talking.** A message in General starts a new chat in a new topic, named after the message's first line until Hermes gives the chat a title; the bot copies the message into the topic and answers in General with a button that opens it. `/new [backend]` and `/new NAME [folder]` start a chat in a new topic too. A message in a topic goes to that topic's chat. A topic that someone made by hand gets a new chat, named after the topic. `/stop`, `/status`, `/where` and `/move` act on the topic's chat. The bot ignores messages from anyone in the group whose Telegram account is not linked to the group's hub user.
- **Following.** The bot follows a topic's chat while it runs, also when it started on the page, in an editor or in a scheduled job, and while someone talks in the topic. It shows the turn that runs when it starts following, not the turns before, and the approvals and questions that still wait. It stops following a chat that has not run and showed no prompt for <!-- docgen:const pkg=internal/telegram name=topicIdle -->`15m0s`<!-- /docgen:const -->.
- **General.** Notices go to General instead of the private chat: scheduled job results, failures, long tasks that ended, and reminders of prompts that still wait, each with a button that opens the chat's topic when it has one. An approval or question of a chat with a topic shows in that topic only, until its reminder.
- **Deleted topics.** When Telegram refuses a message because its topic was deleted or closed, the bot forgets the topic. The chat gets a new topic when it runs again, at least <!-- docgen:const pkg=internal/telegram name=topicIdle -->`15m0s`<!-- /docgen:const --> later.
- **Deleted and archived chats.** When a chat is deleted, in the hub, in Hermes or by an agent, the bot deletes its topic (`deleteForumTopic`) and forgets it. It learns of a delete from the chat's stream when it follows the chat, and otherwise when it checks the topics: when it starts and every <!-- docgen:const pkg=internal/telegram name=reconcileEvery -->`5m0s`<!-- /docgen:const --> after, it asks the backend (`session.info`) about each topic whose chat is not in the chat list, and deletes the topic only when the backend says the chat does not exist; a backend it cannot reach deletes nothing. Archiving a chat closes its topic (`closeForumTopic`), and taking it out of the archive opens it again. A topic that Telegram says is gone is forgotten. When the bot lacks the rights, it says once in General that it needs "Manage Topics" and "Delete Messages". It never closes or deletes General.
- `/unlink` in the group stops all of this. `/help` in the group lists the commands.

The bot needs to be an admin to see every message in the group (with Telegram's privacy mode, the default, a bot that is not an admin sees only commands and replies to its own messages) and to make and rename topics. Every member of the group sees each topic, so keep the group to yourself.

## Notifications

The hub tells each person on their phone when their Hermes needs them or is done, without a hub page open. A notice goes to the person's linked Telegram chat (when `telegram.enabled` and they linked Telegram) and to each browser where they turned on notifications (Web Push, with `notify.vapid_private_key`). These events notify:

| Event | Default | When |
|-------|---------|------|
| Approvals | on | Hermes asks before it runs something (`approval.request`) |
| Questions | on | Hermes asks the person to choose or answer (`clarify.request`) |
| Failures | on | A turn ends with an error, a scheduled job fails or cannot deliver its result, or an unattended run could not use a tool that needs the person |
| Long tasks done | off | A reply that ran for <!-- docgen:const pkg=internal/service name=longTurn -->`2m0s`<!-- /docgen:const --> or more is ready |
| Scheduled jobs | off | A scheduled job (Hermes cron) finished |
| Claude sign-ins | on | A Claude account that a chat uses lost its login (only for the backend's Claude admins, see [Claude](#claude)) |

Each person picks the events, the channels and quiet hours under Settings, Notifications on the page. During quiet hours the hub sends nothing; an approval or question that still waits afterwards gets its reminder then. "Send a test" sends one test notice to each channel, at most once a minute.

What the hub watches:

- **Chats that someone follows.** Every replica reads the approvals and questions of the sessions that it follows for a page or a Telegram chat.
- **Chats nobody has open.** One replica (the holder of the `notify` leader lock, as for the Telegram bot) lists each backend's live sessions every `notify.watch_interval` (default 15s) and follows each one that runs until it stops, so it sees the approvals and questions of a chat that VS Code, the terminal or a scheduled job started. A prompt that was raised before the hub followed the chat comes from the session's snapshot.
- **Scheduled jobs.** The same replica reads each backend's `/api/cron/jobs` through the Hermes web server every `notify.job_interval` (default 1m) and sends a notice for each run that it had not seen: done, failed, or result not delivered. A failure whose error names a login (such as "log in", "401" or "unauthorized") says that the job needs the person to sign in again. The Telegram notice quotes up to 300 characters of the error, with long runs of token characters (24 or more, as in API keys) replaced by `[hidden]`. The first read of a job only records its last run.
- **Unattended runs.** Hermes does not ask anyone in a scheduled job or a one-shot query. hermes-device's browser tools refuse a step that needs an approval in such a run at once (hermes-device `docs/browser.md` section 7.3), and the hub does not change that. When a refusal shows in a chat that the hub follows (a tool result with both "<tool> was not run:" and "no user is present in this run"), the person gets a failure notice that names the tool and says to approve it once with Always.

Who gets a notice: each hub user who may use the backend (`backends[].users`, or `backends[].groups` with the groups of their last login). The hub skips a person who has that chat open on a visible page (the page reports this every 45 seconds; it counts for 90 seconds), and on Telegram a person who has a Telegram chat attached to that session, since that chat shows the prompt already. With a linked group, a chat that has a topic gets its approvals and questions only in that topic, and its other notices in General. The store keeps each notice once per person, so two replicas, or a reconnect that replays events, send it once. A person gets at most 20 notices in 10 minutes; the rest are dropped and logged, and get no reminder.

**Reminder.** An approval or question that still waits after `notify.remind_after` (default 5 minutes) gets one reminder. While the person looks at that chat, during quiet hours, or while they are over the limit above, the hub puts the reminder off and tries again later. The hub asks Hermes first whether the prompt still waits. A prompt older than <!-- docgen:const pkg=internal/notify name=maxReminderAge -->`12h0m0s`<!-- /docgen:const --> gets no reminder.

**Telegram.** A prompt in a chat attached to Telegram, or in a chat's topic, shows with its buttons, as described in [Telegram](#telegram). A notice for a chat that no Telegram chat or topic shows goes to the General topic of the person's linked group, or else to each private chat linked to that person, with the same buttons and an "Open in the hub" link. Only that person may press them or answer them with a reply, and only on the message the hub sent; the hub then answers with that person's access, so a press on a chat they may no longer use fails. In an attached chat, anyone linked who may use the backend may answer, and each button works only on its own message, under a random key. In a linked group only the group's own person may. Buttons of older hubs (`ap:` data) do nothing. When the prompt gets its answer elsewhere, is cancelled or expires, the bot edits the notice to say so and the buttons go away. Button data holds only a random ID, never the prompt. The bot keeps what it needs to route replies and show outcomes in memory for a day; after the bot restarts, a reply to an older question goes to the chat as a message.

**Web Push.** The page offers "Turn on for this device" when the hub has a VAPID key. The hub stores each browser's subscription for the signed-in person (at most <!-- docgen:const pkg=internal/web name=maxPushSubscriptions -->`10`<!-- /docgen:const --> each), only from a push service it knows (Google FCM, Mozilla, Apple, Microsoft WNS), so a subscription cannot make the hub send requests to other hosts. Subscribe and remove need the session's CSRF token and a same-origin request, like the rest of the API. A push message carries only the event kind, a fixed title such as "Hermes needs your approval", the backend's name and the address of the chat; never the chat's title, the command or the question. A click opens the hub at that chat, behind the normal login. Logging out on the page ends that browser's subscription, and a page that finds a subscription of another person (whose login ended without a logout) ends it too. A subscription moves to another person only when the browser sends the same keys, which only it has. The hub never logs an endpoint. A subscription the push service reports gone (404 or 410) is deleted.

- Android: Chrome and Firefox show notifications from the browser or from the installed app.
- iPhone and iPad: Safari shows Web Push notifications only for a web app on the Home Screen (iOS 16.4 or later). Open the hub in Safari, tap Share, then Add to Home Screen, open it from there, and turn notifications on in Settings.
- Desktop browsers work too.

**Install.** The hub is a progressive web app: `/manifest.webmanifest`, icons in `/static/`, and a service worker (`/sw.js`). The service worker caches only an offline page and its icon. It never caches the hub's pages, API answers or event streams, which need the login. Without a network, the app shows the offline page.

To turn on Web Push, make a key once and keep it; a new key ends every browser's subscription:

```sh
openssl ecparam -name prime256v1 -genkey -noout | openssl pkcs8 -topk8 -nocrypt
```

Put the PEM in `notify.vapid_private_key` (environment variable `HUB_NOTIFY_VAPID_PRIVATE_KEY`) or a file named by `notify.vapid_private_key_file`. `notify.vapid_subject` defaults to `http.public_url`, which must be `https` for Web Push. The hub logs the public key at startup. The hub needs outbound HTTPS to the push services (`fcm.googleapis.com`, `updates.push.services.mozilla.com`, `web.push.apple.com` and `*.push.apple.com`, `*.notify.windows.com`); a network policy that limits egress must allow them. A notice's link opens the hub at `http.public_url`, so the phone must reach that address.

## Devices

With `device.enabled` the hub is the server side of [hermes-device](https://github.com/USA-RedDragon/hermes-device) v0.1.0, as its `docs/protocol.md` describes. The hub imports that module's `protocol` and `assertion` packages for the wire names and the hub assertion.

- **Pairing.** `hermes-device login` calls `POST /api/device/pair` and shows a code and the link `<http.public_url>/device/pair`. The user signs in there, types the code, checks the computer's name, system, address and request time, names it and confirms. The code never comes from the link, so a link someone else sends cannot pair their computer with this user. The device then gets its token from `POST /api/device/pair/token`, once. The hub keeps only the SHA-256 of the token. The hub limits pairing requests per address and wrong codes per user (10 in 15 minutes).
- **Backend.** Each device is pinned to one backend at pairing: one with `backends[].devices: true` that the user may use. On every request and every WebSocket upgrade, and again every `device.recheck_interval` while a connection is open, the hub checks the token, that the device is not revoked and that its user may still use the backend.
- **Legs.** `/api/device/exec` goes to the device plugin on the gateway listener (`/api/plugins/device/ws`) and `/api/device/acp` goes to the backend's acp-host (`backends[].acp_url` + `/acp`). For each upgrade the hub signs a new Ed25519 assertion (header `X-Hermes-Device-Assertion`, valid 30 seconds, with a random nonce). The exec leg copies messages unchanged both ways; the ACP leg follows the rules below. `/api/device/gateway` goes to the gateway's `/api/ws` with the hub's own dashboard login. The hub pings every hop every 25 seconds and closes a hop that gives no pong in 15 seconds with 4408.
- **Browser control.** hermes-device can let the agent use the user's Firefox. Its messages ride the exec leg, which the hub copies unchanged. The browser has no sign-in of its own: the device authorizes it, as it does commands. The extension talks only to the local daemon, whose socket only the same OS user can reach, and the daemon is paired to its owner here. The plugin sends browser requests only on the exec leg of a chat's browser device, which must belong to the chat's hub user (the plugin reads each device's user from the hub's signed assertion), and a chat is bound to a computer only by that computer, by its owner here, or by the plugin's `/device` command, which refuses another hub user's computer, so browser requests reach only the user's own computers. The hub does not check browser requests itself, as it does not check commands.
- **Gateway leg rules.** A device token is not operator access to the backend. The hub reads every JSON-RPC message on the gateway leg and applies the rules itself. `session.create` runs in the plugin's placeholder directory with the device directory as its row cwd, and its answer waits until the session is bound to the device; a failed bind deletes the session again. A retry with the same `request_id` gets the same session without a second bind. Before it binds, the hub asks the plugin how it resolves the new session, so a create that returns an existing session of another device is refused, not bound; after a failed bind it deletes only a session that resolves to no device with none in its lineage ever bound. Every request that names a `session_id` needs that session bound to this device (through its lineage), and every `session.resume` is checked on its answer. A resume needs a non-empty `session_id`: one by `title` or `latest` is refused, since the gateway would attach the session before the hub could check it. The hub lets through only an allowlist (`gatewayRules` in `internal/device/rpc.go`): the methods the Hermes Ink TUI and classic CLI send for chatting. It refuses the other methods they send, with the reason in the error message (`<method> is not available through hermes-device: <reason>`): those that run programs or read or write files in the pod (such as `shell.exec`, `process.*`, `reload.mcp`, `session.save`, `paste.collapse`, `rollback.*`, and `image.render`, which reads an image at any path in the pod for the TUI's inline previews), change the whole profile, its credentials or its account (`tools.configure`, `skills.manage`, `model.save_key`, `connectors.*`, `billing.*`), use the pod's audio (`voice.*`, `wake.*`), legacy methods the gateway refuses on the hub's connection anyway, and every method no client sends. It refuses `delegation.status`, `spawn_tree.list` and `spawn_tree.load`, which read every session's subagents and spawn trees. In the answers of `session.list`, `session.active_list` and `session.most_recent` it keeps only the device's own sessions (bound to it through their lineage); a session whose binding it cannot read is left out. It refuses these params: `title`, `base_url`, `api_key` and `accept_hooks` on `session.create` (an existing session, the profile's key sent to a host the device picks, profile-wide hook consent), `cwd` and the `project` key on `config.get` (git in a pod directory), `api_key` on `session.resume`, `staged_upload` on `file.attach` (a browser upload in the pod), and `picker`, `workspace`, `title` and `include_hidden` on `session.list` (the first prompt and last reply of every chat of the backend, chats by another device's folder, a chat by its title, hidden chats). It drops `cwd_explicit` from a create and `refresh` from `model.options`, clamps the sizes of `learning.frames` and `pet.cells`, and refuses a `request_id` that starts with `hermes-hub-`. A device message with no `method` goes to the gateway only as an answer to a gateway request (a string `srq-` id and exactly one of `result` and `error`), rebuilt from those members. It also refuses `session.mutate` operations other than rename, archive, sidebar, model, reasoning, workspace, edit_policy, delete, rewind, reset, branch and compress, requests with any non-null `profile`, `config.set` keys that change the profile (only `busy`, `verbose`, `show_reasoning`, `service_tier`, `fast`, `yolo` without `scope`, and `reasoning` with an exact effort or `reset` in session scope pass), and slash commands outside a short list of session commands (`SlashCommands` in `internal/device/rpc.go`), or with an argument that Hermes reads as `--global` (quoted, upper case or with a Unicode dash too). The same list applies to a `prompt.submit`, `prompt.replace_queued`, `session.steer`, `session.redirect` or `prompt.btw` text that Hermes would read as a slash command (after leading whitespace and `@file:`-style lines, `/cmd@bot` too, aliases counted as their command). `/usage` takes no argument (`/usage reset` redeems an account credit). A `/model` through `slash.exec` or `command.dispatch` gets `--session` put first, where no value flag can take it, and one typed as text is refused: otherwise Hermes may write the pick to the profile's config. When the hub refuses a create's answer, it detaches the subscription the gateway opened with it. The hub forwards each device request under an id of its own and gives the answer the device's id back.
- **ACP leg rules.** The hub reads every JSON-RPC message on the ACP leg (one per WebSocket message) and does not rely on acp-host's checks alone. A device may send `initialize`, `authenticate`, `session/new`, `session/list`, `session/load`, `session/resume`, `session/fork`, `session/prompt`, `session/set_mode`, `session/set_model` and `session/set_config_option` as requests and `session/cancel` as a notification; other requests get `-32601` (reason `hermes_device_denied`) and other notifications are dropped. Each method's params may have only the members the ACP SDK (v0.9.0) defines for it, by alias or field name; any other member, `_meta` above all, is refused with `-32602`, as is a `field_meta` member at any depth: the SDK merges a top-level `_meta` into the handler's arguments, where it would replace the session id or cwd the hub checked. Every one of these except `initialize`, `authenticate`, `session/new` and `session/list` must name its session in `sessionId` or `session_id` (both are checked when both are sent), and the session must be bound to this device, through its lineage, or have been created by `session/new` or `session/fork` on this leg and not bound to another device since. Otherwise the answer is `-32602` with reason `hermes_device_other_device` or `hermes_device_not_bound`. As acp-host does, the hub sets `cwd` to the plugin's placeholder, sets `mcpServers` to `[]` and removes `mcp_servers` on new, load, resume and fork, replaces `resource_link` prompt blocks with a text note, refuses a prompt with any text that is a slash command outside the gateway leg's allowlist (hermes acp sends those to the gateway as `slash.exec` over its own connection), except `/discard` and `/tools`, which hermes acp answers for the session itself (`/discard <id>` clears a turn lost in a gateway restart, which blocks every later prompt of the session), and keeps only sessions bound to this device in `session/list` answers. From acp-host, the hub relays `session/update`, `session/request_permission` and `elicitation/create`, and answers any other agent request (such as `fs/read_text_file` or `terminal/*`) with `-32601` itself. The hub forwards each device request under an id of its own and drops answers to ids it did not send.
- **Sandbox devices.** `backends[].service_devices` lists devices the hub knows from its config, such as each user's sandbox pod running `hermes-device run`. They sign in with their configured token (the hub keeps only its SHA-256), are pinned to their backend, and may use only the exec leg and whoami: the gateway leg, the ACP leg and the bind API answer 403. Users who may use the backend see them in Settings as Sandbox, with whether each is online; they cannot remove them there.
- **Bind API.** `PUT` and `DELETE /api/device/sessions/{id}/binding` go to the plugin with the token's device id. A device can bind sessions only to itself and unbind only its own bindings. Before a bind the hub asks the plugin how it resolves the session through its lineage, and forwards the bind only when the session resolves to this device, or to no device with no session in its lineage ever bound. It answers `409` `bound_to_other_device` for a session that resolves to another device, including one that only inherits that binding, and `409` `was_bound` for one that was bound before and is not now, or whose lineage the plugin cannot read, unless a leg of the same hub replica created the session for this device in the last hour (a branch child or an ACP session whose lineage row is not written yet). So a device that unbinds its own session cannot bind it again.
- **Chats on a computer.** Under New chat, "New chat on a computer" lists the user's computers that are online (paired devices, not sandboxes) and browses the folders in each computer's roots through the plugin's dirs route, with the recent folders of that computer first (the hub keeps the last 8 per computer). The hub starts the session as the gateway leg does: `session.create` in the plugin's placeholder with the device directory as its row cwd, then the bind, before it answers, so no prompt reaches the session unbound. A failed bind deletes the session again. A plain New chat does not change: it runs where the plugin's fallback puts it, such as the sandbox.
- **Where a chat runs.** The chat list and the line under the chat title show the computer and folder of each chat, or Sandbox, and whether that computer is online. The hub reads `GET /bindings` once per backend and asks `GET /sessions/{id}/binding` only for chats without a binding of their own (such as a compressed chat that follows its parent), and keeps those answers for 5 minutes. For a chat whose computer is offline, the page says that messages fail until it is back; the hub does not hold them (holding is only for a backend that restarts). A chat that was never bound shows as Sandbox when the plugin's fallback is the sandbox, and as on the Hermes server otherwise; the plugin's answer does not tell the hub when its fallback is `refuse`.
- **Moving a chat.** "Move to computer..." in a chat's menu, or a tap on the line under its title, binds the chat to a computer and folder of its backend; it then no longer uses the sandbox. A chat on another of the user's computers is unbound from it first, and bound back if the new bind fails. "Stop using this computer" unbinds it: as the plugin rule says, the chat then runs no commands anywhere, also not in the sandbox, until it is moved to a computer again. The hub refuses to move or unbind a chat that runs on someone else's computer, also one that follows a parent chat there, and refuses to unbind a chat whose parent chat is on a computer, because the chat would then follow the parent instead of stopping.
- **Telegram.** `/devices` lists the user's computers, `/new NAME [folder]` starts a chat on one (no folder: the last folder used there, else its first root; `~/x` is under its home, `x` under its first root), `/where` says where the attached chat runs, `/move NAME [folder]` moves it, and `/move off` unbinds it after a confirmation. `/sessions` shows where each chat runs and which ones an editor or the terminal started.
- **Your computers.** Settings on the chat page lists the user's computers with when and from where each was last used, a note when one connected from a new address, how its last exec leg ended (close code, reason, and whether the computer, Hermes or the hub closed it) until it connects again, and Remove. For example, a computer whose hermes-device release does not match the plugin shows the plugin's `4426` reason. Every leg close is logged as `device leg closed` with `code`, `reason`, `backend_code` and `closed_by`. Remove closes the computer's connections at once on the replica that served the page, and on other replicas within `device.recheck_interval`.
- **Replicas.** Devices, pairings and wrong-code counts are in the store, so any replica serves any request. A device's legs may run on different replicas; the plugin and acp-host are the meeting point. The pairing request limit per address counts per replica. On shutdown the hub closes every device connection with 1001, and the devices reconnect, to another replica when there is one.

Set up: make a key with `openssl genpkey -algorithm ed25519 -out hub-device.pem` and give its PEM to the hub as `device.signing_key` (environment variable `HUB_DEVICE_SIGNING_KEY`) or `device.signing_key_file`. Give each Hermes pod only the public key (`openssl pkey -in hub-device.pem -pubout`); the hub also logs it in base64 at startup. Set the plugin's `backend_id` and acp-host's `acp-host.backend-id` to the hub's backend id. Give `/api/device/` a route rule with request and idle timeouts off, as for the event stream. Allow the hub to reach each backend's acp-host port (9130).

## Agent messages

The user's agents can message each other through the hub, as Claude Code sessions do: a chat, or a subagent that a chat delegated to, lists its peers and sends one of them a message, and the target can answer the same way. It does not matter which computer each chat runs its commands on: a message goes from Hermes to the hub and back to Hermes, never through a device. The agent's tools come from the hermes-device plugin (`agent_peers`, `agent_send`, `agent_set_name`, hermes-device docs/protocol.md section 12). The hub takes their calls from the plugin with a long poll (`GET /api/plugins/device/agents/requests`, with the hub's dashboard login), so Hermes needs no way to reach the hub.

- **Scope.** An agent reaches only the chats of its own backend and the subagents of its own delegation tree. Each person has their own backend, so one person's agents never reach another person's. A backend with devices has agent messages on when `backends[].users` names exactly one user and `groups` is empty. A backend that several people share needs `backends[].agent_messages: true`: Hermes does not record which person a chat belongs to, so all its chats then count as one person's, which they already are to the hub (every user of a backend sees and drives every chat on it). `agent_messages: false` turns it off. Only chats of the hub, an editor or the terminal count (session source `gui`, `local`, `cli`, `tui`, `acp` or `desktop`): conversations that Hermes holds itself on a messaging platform, such as a Telegram group, may have other people in them, so agents never see or reach them. The router polls a backend's plugin only when the plugin's `backend_id` is that backend's id.
- **Addressing.** `to` is a session id, a chat's short name (`agent_set_name`, unique per backend), an exact chat title, a subagent id (`sa-...`) or `parent`. A session id always wins. A name may not equal another chat's id or title, and a name of one chat that equals the title of another is refused as ambiguous, so a chat cannot take another chat's messages by its name. `agent_peers` shows each chat's id, name, title, computer and folder (or the sandbox or the Hermes server) and whether a turn runs, newest first, at most 30, without archived chats and chats older than 7 days that are not live.
- **Delivery.** A message to another chat is a new input of that chat (`prompt.submit` under the submission id `hermes-hub-agent-<id>`): an idle chat starts a turn, a busy one runs it after its current turn. A parent's message to its own running subagent is Hermes's steer, which the child reads after its current step. A subagent's message to its parent, or to a sibling, rides on the target's next tool result while the target runs; a parent chat whose turn does not run, or ends before it reads the message, gets it as a new input. A chat that runs on someone's computer runs what the message leads to with that chat's own binding and approvals, never the sender's. The hub refuses to deliver an input to a chat in yolo mode (`config.get` `yolo`), since what the message leads to would then run with no approval the user sees; a chat whose mode it cannot read is refused too.
- **Marking.** The target gets the first line `[Agent message am_<id> from <sender>]` and a paragraph that says another agent wrote it, not the user, that it is not the user's instruction or approval, and that a reply in its own chat does not reach the sender, so an answer goes through `agent_send`. The page shows such a message with the tag "Agent message from ..." and the sender's `agent_send` call with "Agent message to ...", so the traffic shows in both chats. The Telegram bot sends an incoming agent message to the Telegram chats attached to the target. The hub drops control and format characters (zero-width and bidi ones too), turns `@file:`-style references into a full-width `＠`, so the text cannot read files into the target's context, and turns each `[` that could open a frame marker (one that no word character or closing bracket precedes and a letter or `/` follows, such as `[OUT-OF-BAND USER MESSAGE`, `[System note:` or `[Agent message`) into a full-width `［`, so the text cannot fake the end of its frame or a note from Hermes. Devices may not submit inputs under `hermes-hub-` submission ids.
- **Approvals.** A message is text in the target's context, so it can never answer an approval: Hermes takes an approval only from `approval.respond`, which only the user's page, Telegram chat or editor sends. Approval prompts of a turn that a message started go to the user as always. A model can still follow what a message says; the frame tells it not to take the text as the user's words, but the target's approvals are the boundary. The hub checks only the chat's own yolo switch: with Hermes's `approvals.mode: off` for the whole profile, every chat runs without approvals, agent messages included.
- **Limits.** A message has at most <!-- docgen:const pkg=internal/agents name=MaxText -->`8000`<!-- /docgen:const --> characters. A chat and its subagents send at most <!-- docgen:const pkg=internal/agents name=MaxFromTree -->`20`<!-- /docgen:const --> messages, and at most <!-- docgen:const pkg=internal/agents name=MaxPair -->`8`<!-- /docgen:const --> to one target, in <!-- docgen:const pkg=internal/agents name=ShortWindow -->`10m0s`<!-- /docgen:const -->; the agents of a backend send at most <!-- docgen:const pkg=internal/agents name=MaxBackend -->`200`<!-- /docgen:const --> in <!-- docgen:const pkg=internal/agents name=LongWindow -->`1h0m0s`<!-- /docgen:const -->. `agent_peers` and `agent_set_name` are limited to 30 calls per chat tree in 10 minutes on each replica. The hub handles one send at a time per replica, so two sends cannot both pass a limit; two replicas can still each pass one. A message counts one hop more than the highest hop that any agent of the sender's tree (the chat and its live subagents) got in the last <!-- docgen:const pkg=internal/agents name=HopWindow -->`30m0s`<!-- /docgen:const -->, or than the message it answers (`reply_to`); past <!-- docgen:const pkg=internal/agents name=MaxHop -->`6`<!-- /docgen:const --> hops the hub refuses and tells the agent to stop and tell the user. The tool's description tells agents not to answer just to acknowledge.
- **Record.** The hub keeps every message (sender, target, hop, text, how it was delivered) in its store for 30 days and logs each one as `agent message` without its text.

## Deploy

- One replica: the default `store.driver: sqlite` keeps everything in the file `store.path`. Put it on a persistent volume and use the `Recreate` strategy.
- Two or more replicas: set `store.driver: postgres` and `store.dsn` (environment variable `HUB_STORE_DSN`). Connect to the database directly, not through PgBouncer in transaction mode, because the Telegram leader lock needs a session. Each replica keeps its own gateway subscriptions; a page that reconnects to another replica gets a fresh snapshot.
- To move from SQLite to PostgreSQL, set `store.import_path` to the old `store.path` for one start with the old volume mounted. The hub copies the rows once and records that in the database; later starts skip the copy, also when the file is still there.
- On `SIGTERM` the hub makes `/readyz` fail, keeps serving for `shutdown.drain_delay` (default 5s) so load balancers stop sending it requests, gives up on held messages (the chat says they were not sent), tells every event stream to reconnect, stops the Telegram bot (which frees its lock), and then waits up to `shutdown.timeout` (default 20s) for open requests. Keep the pod's termination grace period above the sum of the two.
- Give `http.public_url` the address that users open. It sets the redirect URI, the only allowed `Origin`, and `Secure` cookies (for `https`).
- The event stream is a long-lived HTTP response. Turn off the request timeout on the route (Gateway API `timeouts.request: 0s`). The hub sends a comment every 15 seconds, so idle timeouts above that are fine.
- `/healthz` answers `ok` without a login. `/readyz` answers `ok` once the hub has started, and 503 from the moment it starts to shut down; use it as the readiness probe.
